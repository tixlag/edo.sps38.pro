# Загрузка HEIC/HEIF с преобразованием в WebP

Дополнение к [утверждённым артефактам и доставке](edo-approved-artifacts.md).
Реализовано 2026-10-23 в той же feature-ветке. Merge и deploy не выполнялись.

## Поведение

Все входы DocumentUploadService (загрузка кандидата, собственных документов,
операторская загрузка) принимают одно изображение HEIC/HEIF с HEVC-сжатием.
Тип определяется по содержимому контейнера и метаданным декодера, а не по
расширению или MIME браузера. AVIF и остальные новые форматы не добавлены.
Контейнер с несколькими самостоятельными изображениями отклоняется, чтобы
не потерять страницы. Служебные tiles/alpha/thumbnail HEIF не являются отдельными
документами; декодер собирает основное изображение.

Преобразование выполняется **один раз при загрузке**, до S3, OCR и подтверждения.
Хранимый исходник версии — канонический WebP с правильными MIME, именем, размером
и SHA-256. Отдельная бинарная копия HEIC не сохраняется; его исходные имя,
MIME, размер и SHA-256 сохраняются как происхождение. Временный HEIC и PNG
удаляются при завершении/ошибке загрузки штатной очисткой staging-каталога.
Ссылки просмотра и скачивания возвращают WebP. OCR получает этот же WebP;
координаты относятся к нему. Это не изменение OCR-адаптера или модели.

JPEG/PNG/WebP/PDF по-прежнему сохраняются побайтово. В v2 одиночный WebP получает
отдельную неизменяемую S3-копию при подтверждении; комплект становится PDF.
V1 по-прежнему получает PDF/Base64. Повтор доставки не перекодирует HEIC,
не меняет утверждённый файл, transport или ключ идемпотентности.

## Размер и качество

Разрешение не уменьшается, пропорции и весь кадр сохраняются. Повороты и
отражения irot/imir применяет libheif. Для старого HEIC без такой ассоциации
поворот читается из EXIF IFD0; двойной поворот исключён. Цветовой ICC-профиль
декодированного PNG учитывается при переводе в sRGB для обычных WebP-клиентов.
EXIF/GPS удаляются после применения ориентации. Выход — обычное 8-битное sRGB
изображение; сохранение HDR/gain-map и исходного широкого цветового охвата
не обещается. Для документов проверяется читаемость SDR-представления.

Сначала создаётся lossless WebP (effort 6, exact). Затем сравниваются кандидаты
near-lossless quality 80 и quality 92 (alphaQuality 100, smartSubsample).
Выбирается **минимальный по размеру вариант, прошедший проверку**, иначе остаётся
lossless. Проверка сравнивает каждый пиксель с полноразмерным декодированным
sRGB-оригиналом: средний SSIM блоков 8×8 ≥0,995, RGB PSNR ≥40 dB и независимый
MSE на контрастных границах текста ≤6,5025. Alpha должен совпадать буквально.
Это консервативные численные ограничения, а не гарантия OCR на любых фото.
Текст, печать, подпись и QR включены в синтетические эталоны.

HEIC уже хорошо сжимает фотографии. WebP может оказаться больше исходного HEIC;
процент экономии не является критерием приёмки. Действующие ограничения не
расширены: вход и выход ≤10 МиБ/файл, комплект ≤50 МиБ, ≤10 файлов,
≤100 страниц, изображение ≤40 Мп. Выход сверх лимита отклоняется с HTTP 413,
без повторного агрессивного сжатия или ресайза. Например, шумный синтетический
12-Мп снимок дал выход более 10 МиБ и был корректно отклонён.

## Изоляция и эксплуатация

В API-образ добавлен `libheif-tools` с HEVC-декодером (проверен Alpine 3.23,
libheif 1.23.0). Обычный prebuilt sharp не декодирует HEVC: наличие sharp само
по себе недостаточно. При запуске API вне Docker нужен `heif-convert` в PATH;
его отсутствие даёт HTTP 503 `HEIC_DECODER_UNAVAILABLE`, остальные форматы работают.
Новые npm/Python runtime-зависимости не добавлены.

Один отдельный Node-процесс конвертера на API-процесс. Он использует native
heif-convert без shell. Декодирование ограничено 15 секундами, вся операция —
60 секундами; операции sharp тоже имеют deadline. Завершение/ошибка/timeout
останавливают принадлежащие запросу процессы. libvips cache изолирован от API.
Параллельная HEIC-конвертация возвращает 429 `HEIC_CONVERSION_BUSY`; повторять
с тем же ключом загрузки. Очередь в памяти не накапливается.

JS heap помощника ограничен 64 МиБ; это **не предел всей native-памяти**.
Полноразмерные RGBA-буферы/декодер требуют дополнительную память пропорционально
пикселям. Лимит 40 Мп и единичная конкурентность ограничивают нагрузку, но лимит
памяти контейнера и таймауты reverse proxy нужно проверить на целевом стенде.
Общий таймаут HTTP-загрузки должен учитывать приём файла и конвертацию.

## Миграция и совместимость

Добавочная `0017_heic_upload_provenance`:

| DocumentVersionFile | Назначение |
| --- | --- |
| sourceFilename | Исходное имя HEIC |
| sourceMimeType | Определённый image/heic |
| sourceSizeBytes | Размер HEIC до конвертации |
| sourceSha256 | SHA-256 байтов HEIC |
| normalization | heic-webp-v1 |

Все поля nullable. Для прежних форматов/строк они остаются NULL; существующие
поля файла описывают фактические канонические байты. Применить штатные миграции
к `edo` до запуска нового API. Старые данные и S3 не пересобираются.

Fingerprint повторной загрузки HEIC использует исходные реквизиты и хеш,
поэтому обновление кодировщика не создаёт новую версию при том же upload key.
Аудит атомарен с изменением состояния, отмечает алгоритм и число конвертаций,
не содержит изображения/EXIF. Права и ограничения доступа сохранены.

При откате остановить приём новых HEIC, сохранить миграцию/строки и уже
сохранённые WebP. Их понимает предыдущая версия API. Уже принятые документы
не отправлять повторно и не удалять реестр доставок/квитанций.

## Проверки и измерения

Синтетические эталоны и manifest находятся в
`apps/api/test/fixtures/heic`; реальных персональных данных нет.
Воспроизведение измерений: из корня
`pnpm --filter @edo/api exec ts-node --transpile-only scripts/benchmark-heic-uploads.ts`.
Нужен native heif-convert. Выходные WebP/PNG/JSON находятся только в `.cache/heic`.
Зафиксированные численные результаты: [JSON](edo-heic-upload-measurements.json).

| Эталон | HEIC, байт | WebP, байт | Изменение |
| --- | ---: | ---: | ---: |
| Документ: мелкий текст, QR, печать, подпись, 600×800 | 84771 | 25788 | −69,58% |
| Тот же документ, поворот 90° | 84782 | 24946 | −70,58% |
| Display P3 → sRGB, 600×800 | 85768 | 25746 | −69,98% |
| Старый HEIC только с EXIF Orientation 6 | 84554 | 24946 | −70,50% |
| Простая прозрачная фигура, 160×200 | 4611 | 54 | −98,83% |

Последний пример показывает корректность alpha, а не типичную экономию фото.
Все выбранные варианты здесь near-lossless 80. У документа SSIM 0,9999947,
PSNR 62,75 dB, edge MSE 0,308. QR проверяется отдельно декодером zxing-cpp.

Дополнительный синтетический документ 3024×4032 (12,2 Мп): HEIC quality 85
523199 байт → WebP quality 92 260228 байт (−50,26%), 12,2 секунды, без
ресайза. SSIM 0,9996984, PSNR 51,86 dB, edge MSE 3,8204. Это замер
на локальной машине, не SLA production.
Размеры зависят от изображения и версии кодировщика, точный процент не зашит
в тесты. Реальную съёмку iPhone, Live Photo/HDR-варианты, Safari и просмотр
WebP в конкретном клиенте 1С следует проверить на разрешённом тестовом стенде.
Боевых документов в 1С эти тесты не отправляют.

Проверено: профильные upload/manual suites — 36/36; общий API-прогон —
556 passed / 2 skipped (не настроен отдельный Redis), 50 файлов. Опасный legacy
lk-real-infra.spec.ts исключён, остальные интеграционные проверки использовали
только одноразовые MariaDB/S3/RabbitMQ. Web — 123/123, root lint/build прошли.
OpenAPI и Orval обновлены штатной генерацией. Миграции 0016/0017 применены к
одноразовой MariaDB 11.4.
