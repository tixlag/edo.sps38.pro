# Исходники распознавания документов

## Проверка наличия документа

Внешний OCR дополнен `POST :8000/document-check`, общей проверкой всех фото и страниц PDF независимо от наличия профиля извлечения полей. На GPU работает одна копия Google SigLIP 2 Base в FP16; модель и политика закреплены в `ocr/`. Классификатор сравнивает полный кадр в четырёх поворотах с описаниями документов и посторонних изображений. Только единогласная высокая относительная оценка `NON_DOCUMENT` вызывает возврат. Неуверенность, техническая ошибка, неполное покрытие страниц или некорректный контракт автоматического возврата не вызывают. Значение 0,99 не является доказанной точностью на документах пользователей.

Описания рабочих столов применяются с дополнительной защитой: исходные описания тоже должны давать оценку постороннего изображения не ниже 0,75 на каждом повороте. Смена изображений или типов документов требует проверки качества на представительной выборке; найденные при эксплуатации ошибки и дополнительные частные фотографии не сохраняются в Git.

При `OCR_MODE=external`, включённом worker и `OCR_DOCUMENT_CHECK_ENABLED=true` новые ручные загрузки всех типов переходят в `OCR_PENDING` и ставятся в существующую очередь. Поддерживаемые три профиля затем получают распознавание полей; остальные передаются сотруднику без полей OCR. Пустое распознавание сохраняет исходники и ручную проверку. Во время проверки изображений подтверждение документа недоступно.

Явное постороннее изображение возвращает всю версию в `RETURNED` с причиной «Документ не надлежащего качества» и номерами фото либо файла/страниц PDF. Причина доступна владельцу в обычном статусе независимо от права на OCR-подробности. Состояние, причина и `DOCUMENT_RETURNED` от системного актора `ocr-document-check` записываются одной транзакцией. Очисткой исходников занимается существующее задание OCR, только после фиксации возврата. Повторная загрузка разрешена. Запоздалый результат или ошибка не отменяют решение сотрудника и не затрагивают новую версию.

`OCR_DOCUMENT_CHECK_TIMEOUT_MS=60000` ограничивает ожидание фильтра, общий `OCR_REQUEST_TIMEOUT_MS` остаётся прежним. `OCR_DOCUMENT_CHECK_ENABLED=false` отключает только фильтр. При ручном запуске/повторе OCR с включённым фильтром разрешены также документы без профиля извлечения полей, с прежними проверками текущей версии, прав и наличия исходников. История автоматически не перепроверяется.

Новая модель скачивается runner автоматически до остановки служб. После успешного OCR-выпуска требуется подтверждение пользователя перед отдельным deploy API/web; `OCR_MODE=external` не включается этой задачей автоматически. Подробности установки, контрольных изображений и отката: `ocr/docs/ci-cd.md`.

Повтор OCR доступен проверяющему через `POST /api/v1/documents/:documentId/versions/:version/ocr/retry` с текущей `revision`. Backend возвращает `canRetryOcr` для отображения кнопки: только текущая версия без принятого решения (при отключённом фильтре — поддерживаемого типа), с завершившейся ошибкой `FAILED`/`REJECTED`, сохранёнными исходниками и включённым внешним OCR. `job: null` не считается ошибкой и не даёт права на повтор. Задача повторно ставится через outbox; введённые реквизиты, время отправки и метаданные решения сохраняются. Действие проверяющего записывается в аудит атомарно с изменениями.

Для успешно загруженных ручных документов без задачи и результата OCR предусмотрен отдельный первоначальный запуск: `POST /api/v1/documents/:documentId/versions/:version/ocr/start` с текущей `revision`. Флаг `canStartOcr` показывает кнопку «Запустить OCR» для текущей версии с сохранёнными исходниками (при отключённом фильтре — поддерживаемого типа). Backend атомарно создаёт задачу и outbox, увеличивает `revision` и пишет `DOCUMENT_OCR_REQUESTED` в аудит. Введённые поля и метаданные отправки не меняются; повторное нажатие с прежней `revision` отклоняется.

В `ocr/` размещены действующие Python-сервисы распознавания паспорта РФ, паспорта Узбекистана и миграционной карты. Это перенос проверенных исходников в общий репозиторий для работы агента.

`ocr/` — единственный поддерживаемый источник и место запуска. Прежние RecognizeUZ, DocRecognizer и промежуточный monorepo-export объявлены legacy. На рабочей машине обе Python-службы и GLM переключены на монорепозиторий; управление и текущие пути описаны в [`ocr/docs/operations.md`](../../ocr/docs/operations.md).

| Компонент | Порт | Маршруты |
|---|---|---|
| UZ и миграционная карта | 8000 | `/recognize`, `/recognize-base64`, `/health` |
| РФ | 8001 | `/parse`, `/parse-id-birthday` |
| Общий GLM OCR | 8083 | `/v1/chat/completions` |

Рабочий UZ — модульная версия `DocumentSpec`/stages, с включённой миграционной картой. РФ — существующий `doc_recognizer_universe.py`. Модели, словари и fallback-алгоритмы перенесены без замены. Старые реализации и обучение отделены в `archive/` и `research/`. Ограничения точности и конфликтующие исторические GPU-зависимости описаны в `ocr/docs/verification.md` и `ocr/docs/installation.md`.

## Начало работы

```bash
cd ocr
# Установка окружений и моделей — по README.
python3.12 -m venv .venv-test
.venv-test/bin/python -m pip install -r requirements-test.txt
.venv-test/bin/python -m unittest discover -s tests -v
python3 scripts/check_repository.py
```

Модели распознавания передаются частным архивом с SHA-256 и устанавливаются в игнорируемый `ocr/models`; публичный классификатор устанавливается отдельно и автоматически по своему манифесту. Документы, результаты OCR, логи, `vendor` и виртуальные окружения игнорируются. Обычный Git clone получает только исходники и манифест. OCR исключён из корневого Docker build context; pnpm/Turbo не устанавливает Python/GPU-зависимости.

Корневой `AGENTS.md` описывает правила ЭДО, `ocr/AGENTS.md` — правила компонента. OCR сохраняет собственные окружения и настройки путей относительно `ocr/`. Перенос исходников не требует запуска production-служб, миграций MariaDB или изменения внешнего CI.

## Граница с ЭДО

ЭДО использует существующие `OcrService`, RabbitMQ и outbox. В режиме `OCR_MODE=external` адаптер отправляет файлы в Python API и проверяет расширенный ответ `ocr_fields`. `OCR_MODE=disabled` по умолчанию сохраняет ручной процесс; автоматическое включение до успешной проверки runner запрещено.

- `OCR_RU_BASE_URL=http://10.10.5.184:8001`, `/parse?doc_type=passport_ru&ocr_engine=paddle&debug=false`.
- `OCR_UZ_BASE_URL=http://10.10.5.184:8000`, `/recognize?debug=false`.
- `OCR_REQUEST_TIMEOUT_MS=240000`, lease worker как минимум на 30 секунд больше.
- Паспорт `6ffb1fd5-8341-11eb-ba8b-00259002db81`: гражданство `ru` → РФ, `uz` → UZ. Миграционная карта `39554ac3-6462-11ec-80cc-002590854e7f` → UZ. Остальные виды/гражданства проходят ручную проверку.

При включённом фильтре после успешного сохранения файлов ручной загрузки версия получает `OCR_PENDING`, а OCR-задание и outbox создаются в той же транзакции. Без фильтра сохраняется прежний `IN_REVIEW`. HTTP-запрос загрузки не ждёт завершения OCR. Ошибки и замечания извлечения полей сохраняют оригиналы для проверяющего; подтверждённый `NON_DOCUMENT` отдельно возвращает всю версию, как описано выше. Подтверждение/возврат отменяет незавершённое задание (`CANCELLED`); поздний результат не меняет проверенную или замещённую версию.

OCR-наблюдения хранятся в `document_version_ocr_fields`, отдельно от реквизитов ERP. `originalValue` содержит типизированную подсказку для инпута, `ocrText` — исходный текст соответствующего поля. `mismatch` сравнивает `submittedValue` с `ocrText` строго, включая регистр, пробелы и формат даты; ручная правка `value` не снимает исходное расхождение. Данные кандидата и OCR остаются отдельными источниками, решение принимает проверяющий.

OCR показан под инпутом; клик подставляет нормализованное значение в черновик. Если кандидат не передал поле, сохранённое значение пусто и у него нет `editedBy`, OCR автоматически заполняет ещё не тронутый инпут. Ввод сотрудника, включая намеренную очистку, не перезаписывается. Автозаполненные значения сохраняются той же кнопкой «Сохранить исправления» перед подтверждением.

Экран получает изменения через SSE; для `UPLOADING`/`QUEUED`/`RUNNING` действует резервный опрос раз в 3 секунды. Конечный статус останавливает опрос; фокус вкладки и восстановление сети перечитывают версию. При OCR-обновлении неизменённых серверных реквизитов черновик переходит на новую ревизию без потери ввода. Изменение реквизитов другим проверяющим сохраняет блокировку конфликта.

Обычная версия и ответы мутаций возвращают только OCR обязательных реквизитов, `raw=null`. Полный результат доступен через `GET /api/v1/documents/:documentId/versions/:version/ocr-details` с правом `20010 — EDO_OCR_DETAILS_VIEW` либо `20009 — FULL_ACCESS`, с обязательной проверкой области документа. В UI это первоначально выключенный режим «Все области OCR» и свёрнутые подробности. Для выдачи отдельного права администратору ЛК необходимо зарегистрировать код 20010 в каталоге прав ЛК и назначать его обычным механизмом; ЭДО не выдаёт JWT и не назначает роли самостоятельно.

Паспорт РФ: серия, номер, дата выдачи, орган выдачи и код подразделения. UZ: номер, даты выдачи/окончания, орган выдачи, имя/фамилия латиницей; `AA1234567` разделяется только по полному шаблону. Миграционная карта: серия/номер/фамилия латиницей. Даты въезда/выезда не подставляются в `issueDate`/`expiryDate`. Несопоставимые и некорректные даты остаются видимыми в OCR-наблюдениях. Геометрия выровненного crop не выдаётся за координаты оригинала.

Python сохраняет прежние поля ответа, добавляя `ocr_fields` без debug. Каждый элемент содержит `name`, `value`, `source`, `paddle_text`, `paddle_confidence` и необязательный массив `regions`. Область содержит `file_index` (0-based в multipart), `page_number` (1-based), `x/y/width/height` (0…1) и `text`. Координаты относятся к отображаемому оригиналу после EXIF/PDF rotation, с обратным преобразованием document warp/orientation и размещения embedded image. Отсутствующие координаты допустимы, в частности при full-page GLM. Всего не более 2000 исходных областей. Старые результаты не получают рамки задним числом: нужно повторное распознавание.

Исходные Paddle-данные фиксируются до GLM/quality/grid fallback; искусственный score=1.0 у GLM не считается confidence PaddleOCR. Внутренние пути/debug не переносятся в публичный OCR-результат ЭДО. Области хранятся в `ocr_regions` со ссылкой на OCR-наблюдение и необязательный реквизит; объединённый сегмент серии/номера не дублируется на превью. Наведение/фокус показывает исходный текст сегмента без изменения инпута; клик связанной области переводит к полю.

## Проверка и выпуск

На машине разработки нет весов: запуск inference и Python OCR-тестов здесь не выполняется. Локально проверяются TypeScript-контракты на синтетических HTTP-ответах, жизненный цикл, UI, миграции в отдельной MariaDB и сборка. GitHub Actions и e2e не запускаются.

Сначала интегрируется расширение Python-ответов. GitLab runner на OCR-машине выполняет unit/HTTP-тесты и реальное распознавание трёх частных документов, проверяя новые поля. Маркер `contracts/ocr-fields-v1.json` связывает проверку контракта с активным релизом: откат на старую версию не требует от неё новых полей. После сообщения пользователя об успехе можно включать внешний OCR при отдельном деплое ЭДО с миграцией 0012; до этого `OCR_MODE=disabled`, `OCR_WORKER_ENABLED=false`. При провале исправляется OCR, интеграция не включается. Доступ к OCR-хосту должен быть проверен из API-контейнера до включения.

## CI

Авторитетный pipeline — внешний `edo.yml@webdevs/ci-templates`. Он подключает `ocr/.gitlab-ci.yml` из коммита ЭДО: проверки `.pre`, затем автоматический deploy на OCR-компьютер для push в защищённую main с изменениями `ocr/**/*`. Используется shell runner с тегом `deploy-ocr-pc`. Управляемые релизы, постоянные модели/окружения, реальные проверки и откат описаны в `ocr/docs/ci-cd.md`. Deploy Node-приложения ЭДО остаётся ручным; GitHub Actions не используются.
