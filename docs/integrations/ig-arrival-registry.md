# Реестр списочных заездов ИГ

Кадровый интерфейс, четыре колонки, фильтры, архив и карточки документов описаны в [реестре для отдела кадров](ig-arrival-registry-hr.md). Ниже — актуальная граница ERP → EDO после восстановления независимости ERP (2026-11-09). Исторические результаты проверок в конце не являются проверкой текущего кода.

## Владение данными

ERP — независимый источник. Пользовательские формы, списочное добавление, повторное добавление, изменение даты и ключа, отмена и запись регистров работают по прежним правилам ERP. Состояние EDO, доступ к адаптации, ошибки служебной проекции и неоднозначная история не вводят запретов на эти операции. Исторические служебные регистры и UUID не удаляются. API читает исходные данные и не вызывает инициализацию или запись проекции.

EDO — потребитель фактов и владелец проверки документов. Отображение факта заезда и разрешение открыть документы — разные решения. Неподтверждённое участие остаётся видимым уполномоченному сотруднику, но не становится основанием для доступа к персональным документам.

## Контракт фактического регистра v2

Тот же ERP GET `ERP_COMMUNICATIONS_URL` (`/candidate-communications`) с `action=ig-arrivals&limit=...&cursor=...` возвращает `contractVersion: 2`, `items`, явный `nextCursor` (null означает конец) и `issues`. Каждая группа содержит `personUid`, nullable `code1c` и полный массив `participations` физлица из `ДанныеПоЗаездамНаУчасткиИГ`. Нет фильтра по доступу к адаптации и требования единственного текущего участия. Несовместимый v1 отвергается до применения данных; ошибка формата не равна пустому снимку.

| Поле факта                  | Значение                                                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `sourceKey`                 | `period\|personUid\|locationUid`, полный исходный ключ регистра                                                         |
| `period`                    | Локальный период ключа `YYYY-MM-DDTHH:mm:ss`, со временем                                                               |
| `arrivalMemberUid`          | Сохранённый исходный UUID либо null; дубли UUID передаются без исправления исходных данных                              |
| `arrivalDate`               | Отдельная календарная дата прибытия либо null; изменение даты не меняет ключ                                            |
| `arrivalDateTime`           | Локальная строка `YYYY-MM-DDTHH:mm:ss` либо null, без UTC-конвертации                                                   |
| `locationUid`               | UUID участка либо null; в `sourceKey` пустая ссылка представлена нулевым UUID                                           |
| `cancelled`                 | Собственное поле отмены исходной строки                                                                                 |
| `latestSiteStatusCancelled` | Nullable признак последнего статуса по ссылке физлица и участку: true — отмена, false — иной статус, null — нет статуса |

Также передаются наименование и код участка, ФИО и код менеджера. Неподходящий для идентификации код физлица сохраняется как исходное значение; канонический `code1c` при этом null и связывание документов запрещено. UUID приводятся к нижнему регистру. `СтатусыИГ.ФИО` — ссылка на физлицо, сопоставления по тексту имени нет. Статус участка не доказывает отмену конкретного участия: он передаётся отдельно, отображается как предупреждение и не заменяет `cancelled` строки. При дублях нельзя произвольно выбрать участие для статуса. Документы принадлежат проверенному физлицу.

ERP передаёт повторяющиеся UUID как есть, без глобального поиска дублей. EDO может показать предупреждение при обнаружении локальной коллизии; она не блокирует документы проверенного физлица. Несериализуемый факт, некорректная идентичность владельца или ошибка чтения запрещают финализацию отсутствий. Факт без ссылки физлица не имеет безопасного владельца для текущей модели EDO: ERP сообщает issue, исходную запись не меняет; это известное ограничение отображения.

## Идентификаторы и документы

Для уникального непустого UUID исходной строки сохраняется существующий `arrivalMemberUid` при совпадении владельца; изменение полного ключа с тем же UUID сохраняет идентичность факта. Старый bootstrap сам не писал UUID в исходную строку, однако последующие формы могли перенести выведенный служебный UUID. Поэтому совпадение исходного и сохранённого UUID не объявляется доказательством происхождения исторических документов: доступ к ним по-прежнему требует отдельной проверки личности, кандидата и однозначности владельца. Чужое участие не передаётся другому физлицу. Для legacy без UUID EDO сохраняет свой идентификатор по точному `sourceKey`; повторный проход и изменение даты обновляют ту же позицию регистра. Документы выбираются по подтверждённому физлицу, независимо от идентификатора участия.

Изменение ключа без достоверного UUID создаёт отдельный факт; старый сохраняется в истории и после подтверждения отсутствия попадает в архив. Коллизия UUID, смена UUID существующего ключа, конфликт личности или несколько возможных участий дают предупреждение, не подменяя проверку владельца карточки. Сохранённые документы, подтверждения и исторические идентификаторы не удаляются и не перепривязываются по совпадению ключа, имени или даты.

Безопасная связь документов требует подтверждённой ERP identity ИГ, совпадения `personUid` и `code1c`, отсутствия конфликта владельца и неоднозначности владельца. При недоступной/несовпадающей identity факт доступен в реестре, но кандидат, действия и документные показатели через эту строку закрыты. Административное чтение реестра требует 20011 либо 20009; прочие проверки владельца и прав документов сохраняются.

## Синхронизация и полнота

ERP не выдаёт искусственную монотонную ревизию при чтении. EDO сравнивает каноническое содержимое и ведёт локальную ревизию; повтор того же содержимого не создаёт новое участие. Применение данных и финализация защищены текущими token/generation и сроком аренды в транзакции. Курсор последнего полностью обработанного физлица и логическое поколение полного обхода сохраняются независимо от поколения аренды: ограничение времени запуска или медленная проверка личности не заставляют каждый раз читать только начало регистра. Признак неполноты переносится вместе с обходом и запрещает финализацию пропаж. Запоздавший worker не может затереть результат нового владельца. Документная связь обновлённого факта разрешается только после завершения успешного полного поколения; неполный проход сохраняет видимость фактов, но не открывает их карточки. Локальная ревизия также меняется при изменении экспортируемого контекста после подтверждения личности, чтобы downstream не получил разные состояния под одной ревизией.

Неотменённые фактические строки показываются в текущем реестре независимо от `CURRENT/NONE/CONFLICT`, `currentArrivalMemberUid`, `igVerified` и допуска к адаптации. Отменённые и отсутствующие подтверждёнными проходами строки доступны в архиве. Исчезновение учитывается только после двух полных успешных проходов; неполный проход не архивирует пропажи. История сохраняется и после исчезновения физлица из выдачи ERP.

Страницы ERP при конкурентной записи не образуют атомарный снимок. Два прохода снижают вероятность временного ложного отсутствия, но не гарантируют транзакционную согласованность всего регистра. Повторные проходы восстанавливают наблюдаемое состояние. `sync.lastCompletedAt` — время завершённого прохода, а не время изменения заезда и не гарантия отсутствия диагностических предупреждений.

Отправка контекста адаптации остаётся отдельной границей. Старые состояния и локальная ревизия используются только для консервативного downstream-представления; ошибка его доставки не блокирует операции ERP и отображение фактов.

## Кадровый API и статусы

Endpoints `/api/v1/candidate-review-queue/ig-arrivals/{groups,participations,locations}` и прежние `ig-arrival-groups`, `ig-arrival-people` сохраняются. Backend DTO → OpenAPI → Orval; frontend использует `@edo/api-client`. Интерфейс переиспользует прежний реестр, четыре колонки и карточку документов. Прежние `ig-arrival-groups` / `ig-arrival-people` сохраняют контракт очереди текущих подтверждённых физлиц, а не перечня всех фактов; полный состав, включая неподтверждённые и неоднозначные участия, доступен через `/ig-arrivals/{groups,participations,locations}`. Общая проверка безопасности связи документов применяется к обеим версиям кадрового API.

Фильтры: `archive=current|archive`, `dateFrom`, `dateTo`, `locationUid`, `q`, `documentStatus`, `needsAttention`, `requirementsAction`, `limit`, `cursor`. Для состава обязателен `groupKey`; курсоры связаны с фильтрами. Количества относятся к участиям, а не уникальным людям во всей истории.

Готовность обязательного комплекта отличается от доставки в ERP. Неизвестные требования не означают готовность; локальное одобрение не считается доставкой без подтверждения. Документные показатели архива относятся к разрешённой текущей карточке (`statusScope=CURRENT_CANDIDATE`), не к историческому снимку документов. `oneCEmploymentStatus=UNKNOWN`: статус по физлицу и участку не доказывает оформление конкретного участия.

Сохраняются правила последнего исправления `7191b1b`: проверенный ранее подтверждённый оригинал с `expiresAt=NULL` учитывается при соблюдении остальных проверок; локальное время выбранного участия сохраняется в URL/карточке и показывается без преобразования часового пояса. Полночь сама по себе не доказывает точность времени.

1. Остановить **все** прежние arrival sync workers до переключения версии контракта.
2. Применить миграцию `20261109010000_ig_arrival_facts_v2` при штатном выпуске EDO; обновить API/web и ERP из согласованных MR !61 / !1510. Миграция сохраняет существующие строки и связи. Закрытые !1493 и !1507 уже включены в !1510, отдельно их выпускать не нужно.
3. Проверить `contractVersion:2` и совместимость обеих сторон; только затем включить синхронизацию. Старый v1 нельзя принимать как пустую выдачу. Rolling overlap старого worker и новой версии не допускается.
4. В тестовой базе 1С проверить добавление, повтор, редактирование даты и ключа, отмену и дубль; затем два полных прохода EDO, архив, отсутствие произвольного доступа к документам, локальное время и подтверждённые оригиналы.

В этой задаче merge, deploy и изменение рабочих данных не выполняются. Runtime 1С требует отдельной проверки на доступной платформе; статические проверки и BSL Language Server её не заменяют. Производительность больших исторических наборов требует проверки на тестовой базе.

## Уточнение владения документами, 2026-11-09

Документы и обязательный комплект относятся к подтверждённому физлицу. Отсутствие или повтор UUID участия, несколько участий, конфликты и предупреждения фактов сами по себе не скрывают его карточку и комплект; проверки личности ERP, владельца, кода, исключения РУ/chat, завершённого прохода и прав сохраняются. Факты с датой и объектом группируются по ним, предупреждение отображается у строки. Передача контекста адаптации остаётся консервативной.

Целевые проверки EDO на выделенной тестовой MariaDB: 16 тестов фактической проекции и реестра, 9 worker и 14 HR; API build и ESLint изменённых файлов прошли. Проверены в том числе отсутствие UUID, повтор UUID без issue ERP, две даты и объекта, перенос даты, комплект без документов, несовпадение ERP identity и продолжение прерванной страницы из 50 физлиц. Тестовые наборы MariaDB используют общие singleton и каталог и запускаются последовательно. Платформа 1С и промышленный объём отдельно не проверялись.
