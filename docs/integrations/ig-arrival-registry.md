# Реестр списочных заездов ИГ

Актуальная кадровая модель после доработки 2026-11-09 описана в [реестре для отдела кадров](ig-arrival-registry-hr.md). Описанные ниже первоначальные тестовые результаты относятся к исходному этапу !61.

EDO проверяет документы; 1С остаётся владельцем заездов, логистики и допуска к адаптации. Реестр не предоставляет операторскую загрузку документов или изменение заезда.

## Контракт и идентичность

Новые GET endpoints под `/api/v1/candidate-review-queue/ig-arrivals`: `groups`, `participations`, `locations`. Старые `ig-arrival-groups` и `ig-arrival-people` сохранены. DTO backend → OpenAPI → Orval; frontend использует только `@edo/api-client`.

Фильтры: `archive=current|archive`, `dateFrom`, `dateTo` (включительно), `locationUid`, `q`, `documentStatus`, `needsAttention`; `limit` 1–100, `cursor`. Для состава обязателен `groupKey`. Курсоры связаны с фильтрами и порядком; изменение живых данных между страницами может переместить строку. Страница не является неизменяемым снимком БД. Поиск объектов ограничен и выполняется сервером по названию, UUID служит только идентификатором.

`arrivalMemberUid` — UUID участия, `personUid` — UUID физлица, `sourceRevision` — строковое представление ревизии полного снимка физлица. Диагностическая строка без участия имеет `arrivalMemberUid=null`; искусственные UUID не создаются. Полномочия проверки ИГ (20011 либо 20009) проверяются сервером; `igVerified` обязателен, допуск к семи шагам не является условием видимости.

Проекция сохраняет все полученные участия, но для реестра учитывает только `lastSeenRevision=person.revision`. Отсутствие участия в последнем полном массиве не означает отмену. Миграция восстанавливает присутствие только по сохранённому `sourcePayload`, ничего не выводит из `currentMemberUid` или ФИО. Отменённые и доказанные исторические участия доступны в архиве; неоднозначные конфликтные участия показываются как проблемы, без вымышленного исторического состояния.

`totalParticipationCount` относится к составу группы в выбранном режиме/периоде, `participationCount` — к результату поиска и фильтров документов/внимания. Это количества участий, а не уникальных людей во всей истории.

## Независимые статусы

- `documentStatus`: UNKNOWN, NO_DOCUMENTS, IN_PROGRESS, RETURNED, APPROVED. В кадровой версии APPROVED означает достоверно принятый обязательный комплект; неподтверждённые требования дают UNKNOWN. Подробные количества и действие берутся из requirements, а не из числа всех имеющихся документов.
- `erpDeliveryStatus`: UNKNOWN, NOT_REQUIRED, PENDING, NEEDS_ATTENTION, CONFIRMED. Подтверждение требует валидной квитанции текущей версии и подходящего транспорта; локальное одобрение не считается доставкой.
- `employmentStatus`: UNKNOWN, IN_PROGRESS, DOCUMENTS_COMPLETED. Последнее означает локальное подтверждённое завершение документов, не факт оформления или прибытия в 1С.
- `oneCEmploymentStatus=UNKNOWN`: надёжного ключа статуса конкретного участия в источнике пока нет.
- `statusScope=CURRENT_CANDIDATE`: документные статусы в архиве относятся к текущей карточке, не к историческому снимку документов. Выбранное участие отдельно сохраняется в URL и показывается в панели.

## Время и совместимость

`arrivalDate` — календарная дата. Новое необязательное поле источника `arrivalDateTime` — локальная строка `YYYY-MM-DDTHH:mm:ss` либо null; отсутствие допустимо. Часовой пояс неизвестен, UTC-конвертация запрещена. Полночь не доказывает точность исходного ввода. В 1С поле обогащается только по подтверждённому UUID участия с повышением ревизии при изменении содержимого; старые неподтверждённые снимки не обогащаются.

`sync.lastCompletedAt` — завершение прохода синхронизации. Это не время HTTP-ответа, изменения записи в 1С или гарантия отсутствия ошибок всех записей.

## Порядок внедрения и ограничения

1. EDO: применить миграцию `20261108010000_ig_arrival_registry_presence` на этапе штатного выпуска, затем API/web из одного commit. Локально рабочую БД не мигрировать.
2. EDO совместим с прежним источником без времени и статусов; обновление 1С не является условием выпуска EDO. Проверить завершение синхронизации и старые payload без нового поля.
3. 1С: сначала исправление разбора даты !1493, затем расширение времени после проверки семи сценариев в `1c-erp/docs/integrations/edo-arrival-context.md` на тестовой базе. При необходимости пересверить общий diff разбора JSON. Наш MR не изменяет регистры или бизнес-процесс управления заездом.
4. После выпуска проверить серверный период/объект/поиск, раскрытие нескольких объектов, архив повторного/отменённого участия, панель и возврат из документа, отсутствие доступа у RU-only, повторы синхронизации и признаки свежести.

Блокер статусов 1С: регистр `СтатусыИГ` имеет ключ физлицо+участок+период, без прямой связи с UUID участия. Для достоверной выгрузки нужна отдельная модель связи и охват всех путей записи. Последний статус человека нельзя присваивать повторному заезду. Runtime 1С на машине разработки недоступен; статический BSL-анализ не заменяет тестовую базу.

## Обязательный порядок обновления источника

Сначала применить миграцию и обновить EDO, остановить ВСЕ прежние sync workers, затем обновлять 1С. EDO можно внедрить со старой 1С. Обратный порядок и rolling overlap старого EDO с новым полем не считаются безопасными: прежний parser отбрасывает arrivalDateTime перед sourceHash/sourcePayload, новый parser учитывает его, и одна ревизия может дать ARRIVAL_REVISION_CONFLICT (даже для null). Equal-revision проверку не ослаблять. Если источник уже обновлён первым, требуется отдельно согласованное восстановление с доказанным повышением исходных ревизий; автоматического безопасного recovery здесь нет.
