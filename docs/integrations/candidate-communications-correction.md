# Корректирующая интеграция переписки кандидатов: контракт v1

Историческое описание предыдущего этапа. Действующий контракт: [приёмка рабочего места кандидата](candidate-workspace-acceptance.md). Описанные ниже operator-grants, send_ack и детерминированная генерация чатов отменены и не входят в текущую поставку; для переписки используется прежний протокол ЛК. Документные upload-grants ЭДО сохраняются.

Единственное общее соглашение для ERP MR !1286, ЭДО MR !16 и ЛК PR #2559.
Включение и production-миграции выполняет оператор отдельно после приёмки.

## Идентичность и каноническая ссылка

ERP владеет связью кандидата с чатом. В ЭДО доверенными идентификаторами служат
ERP `erpUid` и LK `chatUuid`; `Candidate.id` сохраняется при появлении второго
идентификатора. `identityKey` существующей карточки не переименовывается.
`DocumentSubmission` сохраняет пространства `chat:<uuid>` и `employee:<code>`:
квитанция ищется по исходному пространству запроса, независимо от ключа карточки.
Связь с сотрудником подтверждается существующим доверенным контекстом;
совпадение имени/телефона либо одного `code_1c` не объединяет дела.
Два существующих владельца означают явный конфликт; автоматическое слияние,
удаление карточек, документов и квитанций запрещено.

ERP добавляет `erpUid` кандидата в существующий ответ `/Candidate` по UUID чата.
Вариант `/Candidate` по коду физлица использует фактический параметр `code1c`;
UID кандидата из кода сотрудника не выводится. ЭДО передаёт доверенный `erpUid`
во внутреннем подписанном контексте загрузки; браузер не выбирает владельца.

API и форма 1С вызывают одну серверную функцию канонической ссылки под
блокировкой конкретного кандидата. Уже записанный чат сохраняется.
Создание: `POST /candidates/generate?erp_candidate_uuid=<ERP UUID>` с прежней
серверной Basic-авторизацией. ЛК вычисляет UUIDv5 с namespace URL и строкой
`erp-candidate:<ERP UUID в нижнем регистре>`; чат, участники и связь создаются
атомарно. Повтор после потери ответа использует тот же ключ. ERP записывает
ссылку только после проверки ответа; случайный второй чат при повторе не создаётся.

## Операторский доступ

`POST /candidates/operator-grants` принимает от доверенного сервера:

```json
{"chat_uuid":"11111111-1111-4111-8111-111111111111","actor_user_code_1c":"TEST-OPERATOR","can_send":true}
```

ЭДО использует `Authorization: Bearer <LK_CANDIDATE_OPERATOR_TOKEN>`;
ERP server — существующие учётные данные Basic через серверный адаптер.
Ответ: `{ "grant": "<краткоживущий grant>", "expires_at": "<UTC>" }`.
Grant подписан сервером ЛК, действует не более пяти минут и связан с конкретным
чатом, проверенным автором и `can_send`. Пустой серверный секрет запрещает выдачу.
Для чтения допускается пустой автор только при `can_send=false`.
Основной секрет, Basic credentials и произвольный браузерный код автора
не становятся пользовательской идентичностью.

WebSocket: `/ws/candidates/chat?chat_uuid=<uuid>`. ЭДО передаёт grant в заголовке
Authorization; форма 1С может передавать краткоживущий `operator_grant` в query.
Файлы используют тот же grant в заголовке. Срок и полномочия проверяются ЛК.
Все действия соединения ограничены его чатом; подмена переданного автора
отклоняется. Публичный режим кандидата остаётся отдельной capability по ссылке:
он не получает grant и операторские полномочия изменением query-параметров.
Старые пути WS и загрузки не предоставляют анонимный операторский обход.
Токены/grants и содержимое переписки не журналируются.

Для открытой формы 1С сервер периодически перевыдаёт grant после проверки
текущей сессии. Событие `refresh_operator_grant` с `data.operator_grant` обновляет только
действующее соединение с теми же чатом и автором; ЛК заново проверяет подпись,
срок и полномочия. Истёкший доступ закрывается, сообщение автоматически
не повторяется. Успех подтверждается событием `operator_grant_refreshed`
с `expires_at`. Новый grant не позволяет поменять чат или автора соединения.

В ЭДО чтение требует `EdoAccessRule.ACCESS` — «Доступ к ЭДО» и разрешённый
объект. Отправка дополнительно требует `EdoAccessRule.DOCUMENT_REVIEW` —
«Проверка и подтверждение документов» и код автора из проверенного JWT.
Область объектов задают `EdoAccessRule.ACCESS_LOCATIONS` — «Доступ к назначенным
объектам», `EdoAccessRule.ACCESS_ALL_LOCATIONS` — «Доступ ко всем объектам»,
либо `EdoAccessRule.FULL_ACCESS` — «Полный доступ к ЭДО» согласно существующей
семантике. Доступ ко всем объектам не заменяет право отправки.

## Отправка, квитанция и неопределённый результат

ЭДО использует UUID существующей `CommunicationOperation`; форма 1С создаёт
UUID один раз на пользовательскую отправку. Текст:

```json
{"event":"send_message","data":{"operation_id":"22222222-2222-4222-8222-222222222222","chat_uuid":"11111111-1111-4111-8111-111111111111","message":"Тестовое сообщение"}}
```

Файл: `POST /candidates/operator/files`, `Authorization: Bearer <grant>`,
multipart-поля `operation_id`, `chat_uuid`, `message`, `file`.
После сохранения сообщения, entry и записи идемпотентности в одной транзакции
ЛК отправляет адресную квитанцию (тот же объект — HTTP-ответ файла):

```json
{"action":"send_ack","operation_id":"22222222-2222-4222-8222-222222222222","status":"SENT","message_uuid":"33333333-3333-4333-8333-333333333333","chat_uuid":"11111111-1111-4111-8111-111111111111","actor_user_code_1c":"TEST-OPERATOR","error_code":null,"replayed":false}
```

Клиент проверяет operation/chat/actor и ненулевой message UUID для `SENT`.
`new_entry` остаётся broadcast обновлением интерфейса и не подтверждает отправку.
Глобально уникальный ID операции связан с хешем вида сообщения, чата, автора,
текста и, для файла, его байтов, имени и MIME. Повтор идентичного запроса возвращает
ту же квитанцию с `replayed=true`; иное содержимое даёт `OPERATION_CONFLICT`.
`FAILED` обозначает достоверный отказ; `UNKNOWN` — возможное сохранение без
достоверного подтверждения. Для них `message_uuid=null`, есть безопасный
`error_code`. Ошибка авторизации до обработки — HTTP 401/403.
Файловый endpoint возвращает ту же проверяемую квитанцию при HTTP 200 (`SENT`),
400 (валидация), 409 (достоверный отказ/конфликт) и 503 (`UNKNOWN`).
Потеря подтверждения после передачи не вызывает автоматическую повторную отправку.
Внешние провайдеры не получают обещания exactly-once: Telegram `SENT` требует
проверенного `ok=true` и `result.message_id`, явный `ok=false` — `FAILED`,
повреждённый или потерянный ответ после возможной передачи — `UNKNOWN`.

## Подключение и откат

1. Применить добавочные миграции реестра операций ЛК и требуемые миграции ЭДО.
   Не изменять рабочие данные идентичности массовым SQL.
2. Подготовить серверные настройки ЛК и ERP, обновить ЛК с защищёнными путями,
   идемпотентной генерацией и квитанциями. Переход закрывает старый анонимный
   операторский путь; до обновления клиентов операторская отправка недоступна.
   Публичный кандидатский сценарий сохраняется.
3. Обновить ERP API/форму и ЭДО, затем включить настройки переписки оператором.
   До наличия нового контракта ЛК отправка ЭДО должна оставаться выключенной.
   Пустые `ERP_COMMUNICATIONS_URL`/`LK_CHAT_BASE_URL` означают отсутствие настройки
   и не останавливают основной документооборот.
4. Проверить тестового кандидата без внешних транспортов, затем разрешать работу.

Настройки: существующие `ERP_CANDIDATE_URL`, `ERP_CANDIDATE_TOKEN`,
`ERP_USERNAME`, `ERP_PASSWORD`; отдельный `ERP_COMMUNICATIONS_URL`;
`LK_CHAT_BASE_URL`, `LK_PUBLIC_BASE_URL`, `LK_CANDIDATE_OPERATOR_TOKEN`.
Секреты задаются серверно; production-секреты на этом этапе не ротируются.
ERP использует существующий входящий `HTTP_IN_API` и исходящий
`HTTP_OUT_BASIC_03`, без дополнительного ERP-токена.

При откате сохраняются таблицы и записи операций, документы и версии, связи
кандидатов, переписка и квитанции. Откатывается код либо отключается переписка;
старый анонимный операторский endpoint не включается. Не удалять таблицы и
не восстанавливать всю БД ради отката клиента.

## Существующие конфликты идентичности

Диагностика сначала только чтением: сопоставить доверенную ERP-пару UID/чат
с обоими владельцами ЭДО, количеством документов, версий, отправок и квитанций.
Идентификаторы и персональные данные не включать в общие логи/отчёты.
При конфликте заблокировать только спорное действие, сохранить все карточки.
Оператор проверяет источник связи, выбирает каноническое дело и согласовывает
отдельную адресную миграцию с проверкой всех внешних ключей и аудитом.
Автоматическое удаление или объединение по ФИО, телефону и `code_1c` запрещено.

Для диагностики одной подтверждённой ERP-пары используйте параметризованный
запрос только чтения в закрытой операторской сессии. Параметры `?` — ERP UID
и UUID чата; реальные значения и результат не помещать в общие логи:

```sql
SELECT c.id, c.identityKey,
       (SELECT COUNT(*) FROM documents d WHERE d.candidateId = c.id) AS documents,
       (SELECT COUNT(*) FROM document_versions v
        JOIN documents d ON d.id = v.documentId WHERE d.candidateId = c.id) AS versions,
       (SELECT COUNT(*) FROM document_submissions s
        JOIN document_versions v ON v.id = s.versionId
        JOIN documents d ON d.id = v.documentId WHERE d.candidateId = c.id) AS receipts,
       (SELECT COUNT(*) FROM communication_operations o
        WHERE o.candidateId = c.id) AS communications
FROM candidates c WHERE c.erpUid = ? OR c.chatUuid = ?;
```

ERP CI требует реального номера задачи для имени `feature/1C-<номер>-...`.
Текущая ветка `feat/edo-candidate-communications` сохраняется; переименование
MR/ветки и номер YouTrack остаются организационным действием владельца.

Перед разрешением выпуска требуется согласовать с актуальной целевой веткой
конфликты ЭДО: `prisma/schema.prisma`, `manual-document.service.ts`,
`dashboard.spec.ts`, OpenAPI и сгенерированный клиент. Проверка выполнялась

OCR-модели/аудит/`submittedAt`, транзакционную постановку OCR, текущий аргумент
`ConfigService` загрузчика плюс новый отдельный `ErpCandidateClient`, поддержку
документов сотрудника без чата и сериализацию дат документов. После согласования
заново выполнить генерацию и целевые gates на итоговом SHA; не откатывать target
к старой ветке переписки и не удалять данные/миграции. Это условие выпуска,
не разрешение на merge в рамках данного этапа.

Во время первого полного локального API run прежний `lk-real-infra.spec.ts`
загрузил root `.env` и выполнил round-trip в двух созданных им временных очередях
shared RabbitMQ. Тест прошёл путь удаления этих очередей; последующая узкая
проверка только чтения подтвердила отсутствие очередей с его тестовым префиксом.
Cleanup не менял чужие ресурсы. Рабочие
очереди, bindings, volumes и lifecycle bucket не изменялись. Последующие запуски
имели явные изолированные настройки. Поэтому абсолютное утверждение «shared
инфраструктура не изменялась» для всего этапа было бы неверным.

При начальном исследовании диагностический вывод также затронул ранее
существовавшие секреты из исходников/аргументов процессов. Их значения не
переносились в новые файлы, fixtures, коммиты и отчёт; последующие чтения
ограничены. Ротация рабочих секретов в рамках задачи не выполнялась.
