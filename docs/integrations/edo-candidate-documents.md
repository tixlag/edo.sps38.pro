# Документы кандидатов и сотрудников

## Текущий процесс

Внешний OCR включается отдельно после подтверждённого runner: см. [интеграцию OCR](document-ocr-sources.md). По умолчанию сохраняется ручная проверка. EDO получает из ERP карточку кандидата (UUID чата, должность,
гражданство и объект), показывает применимые документы и только обязательные
поля каталога `GET documents-by-positions`. Применимость: совпадение должности **или**
флаг «ВсемРФ»/«ВсемИГ». Гражданство по умолчанию `ru`. В frontend нет списка
обязательных документов или правил по гражданству.

EDO проверяет чат через узкий внутренний API ЛК, получает контекст кандидата
из ERP и выдаёт доступ через `POST /api/candidate-documents/by-chat/{chatUuid}/upload-grant`.
Браузер получает формы, статусы и черновики напрямую в EDO. Фото/PDF и заполненные
поля он отправляет **напрямую в EDO** по URL из этого ответа. Surveys в документных
запросах не участвует. Конструктор адаптации, `{{documents}}` и сегмент `DOCUMENTS`
остаются в surveys: public_next отображает самостоятельный компонент EDO.

Один комплект = один документ. Пока текущий комплект находится в `IN_REVIEW`,
новый комплект этого вида для того же владельца запрещён: backend возвращает
409 `DOCUMENT_IN_REVIEW`, форма блокирует выбор файлов и отправку. Резервирование
и проверка выполняются под блокировкой строки кандидата; вторая параллельная
загрузка до завершения первой получает 409 `DOCUMENT_UPLOAD_IN_PROGRESS`.
Идентичный повтор успешного комплекта с прежним ключом остаётся идемпотентным.
После решения проверяющего загрузка нового комплекта снова разрешена.

Для отклонённой версии браузер ЛК запрашивает напрямую в EDO
`GET /api/candidate-documents/by-chat/{chatUuid}/documents/{documentUid}/draft`.
Возвращаются только ранее отправленные поля текущей `RETURNED` версии данного
владельца; чужие, исторические и неотклонённые версии недоступны. Оба ответа
имеют `Cache-Control: no-store`. Форма подставляет строки с ведущими нулями,
даты и boolean, допускает исправления и сохраняет редактирование при позднем
ответе. Значения находятся в памяти формы, не в постоянном кэше запросов ЛК.

Оригиналы сразу сохраняются в закрытом S3; после
полного сохранения версия получает `IN_REVIEW`. Пользователь видит жёлтую плашку
с часами. Проверяющий открывает `/review`, видит изображения/PDF и значения из
JSON, исправляет поля и подтверждает либо возвращает документ с причиной.
Подтверждение собирает страницы в один PDF, сохраняет его в S3, фиксирует версию,
аудит и задание ERP атомарно. Кандидат видит зелёную плашку с галочкой. Возврат
даёт красную плашку с крестом и просьбой прислать качественное фото; оригиналы
отклонённой версии удаляет фоновая очистка. История версий и решений остаётся.

`submittedValue` неизменяем. `originalValue` зарезервирован для OCR; `mismatch`
сравнивает распознанное значение с присланным и позволяет выделить поле красным.
Сейчас OCR-поля и задания не создаются. Старый маршрут без `metadata` сохраняет
прежний OCR-контракт; при `OCR_MODE=disabled` он возвращает 503.

## Серверные настройки

Корневой `.env` EDO:

- `ERP_DOCUMENTS_BASE_URL=https://api-erp.sps38.pro/ERP/hs/api/`
- `ERP_CANDIDATE_URL`, `ERP_CANDIDATE_TOKEN`: URL `Candidate?uuid=...` и его токен.
- `ERP_DOCUMENTS_TOKEN`, `ERP_USERNAME`, `ERP_PASSWORD`: одновременно заголовок
  `token` и Basic-авторизация; только сервер, не OpenAPI/frontend/логи.
- `EDO_LK_INTERNAL_TOKEN`: входящий отдельный токен ЛК → EDO; отличается от
  `LK_EDO_INTERNAL_TOKEN`, используемого в обратном направлении.
- `EDO_PUBLIC_API_URL`: публичный адрес API с `/api`, доступный браузерам для SSE.
- `CORS_ORIGIN`: origins EDO и ЛК через запятую.
- `DOCUMENT_WORKER_ENABLED=true`: доставка ERP, восстановление прерванных операций,
  очистка S3 и истёкших SSE-доступов. Для экспорта и управляемых тестов `false`.
- `OCR_MODE=disabled`, `OCR_WORKER_ENABLED=false` для ручного процесса.
- `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`.

В chat-server ЛК остаются `EDO_API_BASE_URL` (без `/api`) и
`EDO_LK_INTERNAL_TOKEN` для надёжной доставки привязки сотрудника. В surveys
настройки EDO больше не нужны; его ERP-настройки для адаптации сохраняются.
В public_next: `VITE_EDO_API_URL` — origin EDO без `/api`, по умолчанию
`https://edo.sps38.pro`; для локального API — `http://localhost:3001`.
EDO обращается в ЛК с `LK_BASE_URL` и `LK_EDO_INTERNAL_TOKEN`; соответствующий
секрет PHP — `EDO_INTERNAL_TOKEN`. Эти настройки не передаются браузеру.
Не запускайте воркеры с неполной конфигурацией.

Бакет должен существовать и быть закрытым. Подписанные URL доступны только
проверяющему с правом доступа к документу. Для PDF.js необходим CORS бакета:
GET/HEAD, `Range`, expose `Content-Length`, `Content-Range`, `Accept-Ranges`, `ETag`.
Оператор дополняет существующие правила, не удаляя origins ЛК.

## API ЛК → EDO

Внутренние REST-ручки требуют `Authorization: Bearer <EDO_LK_INTERNAL_TOKEN>`.
Этот токен остаётся на сервере ЛК; браузер получает отдельный ограниченный доступ.

`GET /api/internal/edo/v1/document-catalog?position_code_1c=...&citizenship=ru`
возвращает применимые виды и поля с label/kind/required. Каталог проверяется целиком
до записи в relational-таблицы; при временной ошибке доступен последний успешный
снимок, при отсутствии снимка — 503. Несуществующие в новом снимке виды скрываются.

Срок свежести справочника — 24 часа от последней успешной синхронизации.
Дата берётся из `catalogSyncedAt` в MariaDB и сохраняется при перезапуске API.
При открытии сразу возвращается сохранённый снимок; если он старше суток,
обновление запускается в фоне. При пустой БД первый запрос ждёт загрузки.
Одна общая Redis-блокировка `edo:document-catalog:refresh` объединяет обновления
между экземплярами API. На ошибке блокировка истекает через 90 секунд и служит
общей паузой повторов; дата успешного снимка не изменяется. Если Redis недоступен,
сохранённый справочник продолжает читаться, обновление ждёт восстановления Redis.

В EDO карточка кандидата кэшируется на 15 минут отдельно от справочника.
Общий Redis-кэш ограничен 1000 карточками (LRU), обновление координируется
короткой блокировкой на UUID чата. Параллельные запросы внутри экземпляра
объединяются. При временной ошибке ERP последняя карточка используется с паузой
60 секунд. 404, отказ авторизации и некорректная карточка не маскируются кэшем.
При недоступном Redis выполняется ограниченный запрос ERP без кэширования.
Чат и актуальная связь с сотрудником проверяются в ЛК при каждом новом REST-запросе,
независимо от кэша ERP. Статусы, SSE-доступы и черновики не требуют ERP.

`POST /api/internal/edo/v1/document-upload-grants` принимает проверенный сервером
ЛК контекст: `documentUid`, `idempotencyKey`, `chat_uuid` и/или `code_1c`,
`position_code_1c`, `citizenship`, необязательный `project_code_1c`. Возвращает
`token`, публичный `url` и `expiresAt` (пять минут). Доступ подписан HS256 с
отдельным назначением и ключом, производным от серверного интеграционного секрета;
проверяются подпись, алгоритм, issuer, audience и exp. Он ограничен владельцем,
видом документа и ключом комплекта. JWT входа в ЛК и SSE-токен здесь не подходят.

`POST /api/candidate-documents` — браузерная загрузка напрямую в EDO:

- `Authorization: Bearer <upload-grant>`; только память, без URL/storage/cookies.
- `Idempotency-Key` должен совпадать с ключом в доступе.
- `metadata`: JSON только с `documentUid` и `documentFields`.
- `files[]`: тот же упорядоченный комплект фото/PDF и те же лимиты.

Владелец, должность, гражданство и объект берутся из подписанного доступа;
попытка передать их в `metadata` отклоняется. Вид документа должен совпадать.
CORS разрешает origin ЛК и заголовки Authorization/Idempotency-Key.
Прежний multipart-прокси загрузки в surveys удалён.

`POST /api/internal/edo/v1/documents` остаётся серверным контрактом, multipart:

- `Idempotency-Key`: 1–128 печатных ASCII-символов без пробелов.
- `metadata`: JSON, пример ниже.
- `files[]`: 1–10 JPEG/PNG/WebP/HEIC/HEIF/PDF, смешанный комплект допустим, порядок сохраняется. HEIC/HEIF однократно нормализуется в WebP при загрузке без ресайза; [алгоритм, лимиты, миграция и измерения](edo-heic-uploads.md).

```json
{
  "documentUid": "6ffb1fd5-8341-11eb-ba8b-00259002db81",
  "chat_uuid": "00000000-0000-4000-8000-000000000001",
  "position_code_1c": "000000491",
  "citizenship": "ru",
  "documentFields": {
    "series": "0012", "number": "000345", "issueDate": "2026-10-12",
    "issuedBy": "Орган выдачи", "departmentCode": "123-456"
  }
}
```

Нужен `chat_uuid` либо `code_1c`; допускаются оба для связывания. Необязательные
`project_code_1c`/`locationId` устанавливают область доступа из проекции ЛК.
`position_code_1c` используется только для подбора видов документов и снимка
профиля. Он не подставляется в реквизиты документа. `documentFields.positionUid`
относится к водительскому удостоверению и передаётся только как полученный UUID;
при отсутствии значения поле не заполняется кодом должности кандидата.
Старые клиенты могли прислать сюда код из `position_code_1c`: такое значение
отбрасывается при загрузке, подтверждении и отправке ранее сохранённого payload.
Настоящий UUID сохраняется. Это не запускает повторные отправки в ERP.
Строки сохраняют ведущие нули, флаги — boolean. Поля и даты проверяются
по схеме каталога; неизвестные поля запрещены.
Реквизиты любого документа можно не заполнять: отсутствующие, `null`, пустые и
пробельные значения не препятствуют загрузке и подтверждению, включая паспортный
`departmentCode`. `requiredFields` каталога выбирает поля формы, но не блокирует
отправку. Формат непустых значений продолжает проверяться.

Лимиты: 10 МиБ на файл, 50 МиБ на комплект, 100 страниц, 40 мегапикселей на фото.
Тип определяется по содержимому. Пустые/повреждённые файлы, анимация и зашифрованные
PDF отклоняются. Итоговый PDF ограничен 100 МиБ. Единственный PDF сохраняет байты,
несколько PDF/фото объединяются в порядке multipart с учётом EXIF фото.

202 возвращает documentId/version/submissionId и `IN_REVIEW`. Идентичный повтор
того же ключа возвращает прежние ID. Изменённый комплект с тем же ключом — 409;
после неудачной загрузки нужен новый ключ. Незавершённые загрузки не отображаются.

`GET /api/internal/edo/v1/documents?chat_uuid=...` (либо `code_1c=...`) возвращает
статусы без полей, файлов или персональных значений.

## Очередь проверки по кандидатам

### Очереди РУ и ИГ

`/review` — «Проверка документов РУ», `/review-ig` — «Проверка документов ИГ».
Оба экрана используют один интерфейс, включая возвраты, реквизиты, OCR и доставку
в ERP. РУ: есть связь `chatUuid` в ЛК/ЭДО **или** гражданство `ru`; остальные
кандидаты относятся к ИГ. Распределение вычисляется сервером по локальным полям;
чтение очереди не вызывает 1С и не требует новой миграции. Существующие
кандидаты РУ сохраняют свою группу.

Право `20002` сохраняет номер и переименовано в `EDO_DOCUMENT_REVIEW_RU`;
`20011 — EDO_DOCUMENT_REVIEW_IG` даёт доступ к ИГ. `20009` включает оба.
Регистрация каталога ЛК подготовлена отдельно:
https://github.com/websps/lk.sps38.pro/pull/2596. Назначения существующего 20002
сохраняются; для ИГ нужно назначить 20011 после выпуска каталога ЛК.

`candidate-review-queue`, `review-documents`, `review-candidates` и
`review-documents/facets` принимают `reviewGroup=RU|IG`, по умолчанию `RU`.
Недоступная группа возвращает 403. Профили и версии документов возвращают
серверный `reviewGroup`. Карточки, версии, файлы, SSE и действия проверки
ограничены группой и областью объектов; связь с сотрудником не обходит группу.
Недоступные карточки и документы возвращают 404. Аудит сохраняет самостоятельное
право чтения, но не даёт действий проверки. Собственные документы и гостевые
доступы по чату по-прежнему защищены своей моделью владельца.

1С сохраняет название поля `uuid`: оно содержит UUID чата. При наличии чата
EDO запрашивает `Candidate?uuid=...`; без связи с чатом —
`Candidate?code1c=...` (точное имя параметра 1С; `code_1c` не принимается).
Персональные поля находятся в `candidate`: `candidate.uuid`, `candidate.code1C`,
`candidate.name`, `candidate.birthDate`, `candidate.citizenship`,
`candidate.isReemployment`. `position`, `project`, `manager`, `master`,
`supervisor` и `mentor` находятся на верхнем уровне. ЭДО нормализует карточку
в свой снимок профиля, включая имя и код менеджера из `manager`.
Поля `candidate.sex`, `candidate.photoPath`, имена и коды `master` и
`supervisor` сохраняются в профиле. Пустые значения из 1С не стирают ранее
сохранённые данные. Для неизвестного актуального пола правила исключения не
применяются. После расчёта списка по гражданству и должности ЭДО исключает
военный билет из обязательных документов женщин; сохранённые документы не
удаляются.
Для поиска по коду пустое `candidate.uuid` допустимо, а `candidate.code1C`
должен совпасть с запрошенным кодом. Непустой UUID ответа
дополнительно проверяется через каноническую связь ЛК. Кеши двух способов поиска
используют разные ключи. Пустое гражданство по прежнему контракту нормализуется
в `ru`; явно указанное иностранное гражданство сохраняется.

Для уже сохранённых кандидатов предусмотрена отдельная команда
`pnpm --filter @edo/api candidates:refresh -- --dry-run --limit=20`.
Она повторно запрашивает 1С без использования кеша и выводит идентификаторы
кандидатов и имена изменившихся полей, без значений. Для записи после проверки
используется `--apply`; `nextCursor` из отчёта передаётся как `--after=<id>`
для следующей страницы. При изменении профиля между чтением и записью он
пропускается, ошибки и несовпадение идентичности не меняют данные. Команда не
запускается автоматически при миграции или развёртывании.


Экран `/review` использует `GET /api/v1/candidate-review-queue` с пользовательским
JWT. Ответ содержит кандидатов, а внутри каждого — документы, подходящие под
фильтры очереди:

```json
{
  "items": [
    {
      "candidate": {
        "id": "candidate-id",
        "fullName": "Иванов Иван Иванович",
        "approvedDocuments": 2,
        "requiredDocuments": 5
      },
      "documents": [
        {
          "id": "document-id",
          "documentTypeCode": "PASSPORT",
          "title": "Паспорт",
          "status": "IN_REVIEW",
          "currentVersion": 1,
          "revision": 0,
          "documentUid": null,
          "deliveryStatus": null,
          "pendingDeliveryVersions": []
        }
      ]
    }
  ],
  "nextCursor": null
}
```

В примере профиль сокращён; полный состав полей задаёт `CandidateProfileDto`
в OpenAPI. Вложенные документы не дублируют профиль, `candidateId`, `chatUuid`
или `code1c` владельца.

`limit` (1–100, по умолчанию 50) ограничивает число **кандидатов**. Сортировка —
по `Candidate.id` по возрастанию; `cursor` берётся из `nextCursor` предыдущего
ответа. Внутри кандидата возвращаются все подходящие документы, без отдельной
пагинации: большой комплект не разрывается между страницами. `nextCursor: null`
означает последнюю страницу. При смене фильтров нужно сбросить cursor.

Фильтры профиля (`q`, `candidateId`, `citizenship`, менеджер, наставник, даты
рождения, должность, объект) применяются к кандидатам. `status` и
`documentTypeCode` применяются к вложенным документам; кандидат попадает в
очередь только при наличии хотя бы одного подходящего документа с
`currentVersion > 0`. Статусы: `IN_REVIEW` (по умолчанию), `RETURNED`,
`ERP_PENDING` (есть версия, ожидающая ручной доставки в ERP), `ALL`.
Профиль кандидата и каждый документ проверяются по области доступа вызывающего.
Записи без кандидата в эту очередь не входят.

`RETURNED` выбирает документы, у которых есть хотя бы одна возвращённая версия,
в том числе после повторной загрузки или подтверждения актуальной версии.
`documents[].returnedVersions` содержит историю возвратов от новой версии к
старой: `version`, `rejectionReason` и `supersededByVersion` (номер текущей
версии, если она новее возвращённой; иначе `null`). Текущие `status` и
`currentVersion` документа при этом сохраняют своё значение. В интерфейсе
каждый возврат открывает именно свою версию; файлы возвращённых версий
недоступны, реквизиты и причина возврата остаются доступными для просмотра.

Прогресс `approvedDocuments` учитывает все доступные подтверждённые документы
кандидата независимо от вкладки и фильтра типа. `requiredDocuments` считается
по локальному снимку каталога и профилю; при неизвестной должности — `null`.
Чтение очереди не обращается к ERP и не синхронизирует пустые профили.

Старые профили заполняются отдельной ограниченной командой:

```sh
pnpm --filter @edo/api candidates:backfill -- --dry-run --limit=20
pnpm --filter @edo/api candidates:backfill -- --apply --limit=20
```

Она проверяет каноническую связь чата через узкий внутренний API ЛК,
получает карточку из ERP Candidate через сервис контекста EDO, проверяет
совпадение UUID снимка и использует ту же нормализацию, что загрузка документов. Только кандидаты с документами и пустым
`profileSyncedAt` участвуют в проходе. Карточки без ФИО, неверный контракт и ошибки
LK остаются ошибками отчёта без записи в БД. Максимум — 100 кандидатов и две
минуты на запуск; отчёт содержит ID, статусы и имена полей без персональных
значений. `hasMore` указывает на необходимость следующего ограниченного прохода.

Режим по умолчанию — dry-run; `--apply` записывает профиль и аудит `DATA_IMPORTED`
атомарно в MariaDB `edo`. Короткая транзакция блокирует строку кандидата и
повторно проверяет `profileSyncedAt` и владельца: новая загрузка или параллельный
backfill не перетираются. Команда не меняет документы или связь с сотрудником
и не запускает Nest workers. На проде запускается через
`docker exec edo-api pnpm --filter @edo/api candidates:backfill -- --dry-run --limit=20`.

При `LK_HTTP_503` проверьте внутренний API чатов ЛК и сервисный токен.
При `ERP_CANDIDATE_UNAVAILABLE` проверьте ERP Candidate и серверные настройки EDO;
`ERP_CANDIDATE_NOT_FOUND` означает отсутствие карточки ERP.
Ошибка источника не исправляется запуском `lk:sync`: эта команда синхронизирует
справочники сотрудников и объектов, а профиль кандидата заполняется из отдельной
карточки ERP. После восстановления источника сначала повторите dry-run.

Для карточки используется `GET /api/v1/candidates/{candidateId}`: тот же объект
`{ candidate, documents }`, но со всеми доступными документами с
`currentVersion > 0`, без фильтров очереди. Профиль возвращается и при пустом
комплекте. Кандидат вне области доступа даёт 404; прямые ссылки на карточку
работают независимо от текущей страницы или вкладки очереди.

`GET /api/v1/review-candidates` остаётся поиском для селектора ФИО.
Документные контракты `/api/v1/review-documents` и
`/api/v1/candidates/{candidateId}/documents` сохранены для существующих клиентов;
у старой очереди limit/cursor относятся к документам. После выкладки API нужно
развернуть frontend, использующий сгенерированные hooks новых маршрутов.

## SSE

`POST /api/internal/edo/v1/document-stream-grants` с владельцем выдаёт URL и
случайный token на 5 минут. Браузер передаёт его в Authorization, никогда в URL.
Токен разрешает только статусы одного владельца, хранится на сервере как хеш.
Поток `/api/document-status-events` отправляет начальный снимок, изменения и heartbeat.
При переподключении ЛК получает новый доступ. Каждый экземпляр API читает общую БД;
пропущенный сигнал не теряет состояние. Для длинных JWT таймер истечения разбивается на ожидания не больше `2^31-1` мс,
с повторной проверкой исходного срока: переполнение Node.js не закрывает поток.
Проверяющие используют JWT-поток
`/api/v1/document-status-events` с проверкой прав/объекта и срока JWT.

В ЛК компонент подключён в адаптации, публичном чате кандидата и чате участников.
REST-клиенты сгенерированы из OpenAPI; отдельный SSE transport читает только поток.

## ERP и связь сотрудника

Новые подтверждения по умолчанию используют **`multipart-v2`** (уточнение владельца
задачи 2026-10-23). `ERP_DOCUMENTS_TRANSPORT=base64-v1` явно выбирает прежний
контракт для новых подтверждений. Исторические доставки и строки без признака
транспорта всегда остаются v1, независимо от env. Автоматического fallback нет.

Согласованный контракт 1С: [EDO → 1С v2](edo-candidate-documents-v2.md),
предоставлен владельцем 2026-10-23; исходный файл отмечает границу статических
проверок 1С. Владелец сообщил о готовности рабочей публикации, но агент EDO
не отправлял туда документы и не выполнял реальную приёмку.
Подробные замеры и эксплуатация: [включение, откат и проверки](edo-approved-artifacts.md).

Для v2 один JPEG/PNG/WebP/PDF копируется серверной S3 CopyObject в отдельный
`approved-<uuid>.<ext>` без изменения байтов, EXIF, разрешения или качества.
Копия проверяется потоковым SHA-256/размером; исходник остаётся независимым.
Комплект из нескольких файлов становится PDF: JPEG встраивается как DCT,
PNG — без потерь с alpha, WebP декодируется в PNG без дополнительного сжатия
с потерями; страницы PDF копируются без растеризации, порядок сохраняется.
Для v1 всегда подготавливается PDF. EXIF 1–8 применяется матрицей PDF, без
перекодирования JPEG. Исходные ограничения загрузки не расширены: 10 МиБ/файл,
50 МиБ/комплект, 10 файлов и 100 страниц. Итоговый артефакт ограничен 100 МиБ.

При подтверждении в одной транзакции сохраняются approved-метаданные версии,
замороженные реквизиты/транспорт единственной `ErpDocumentDelivery` и аудит.
Повтор доставки читает этот объект, не вызывает подготовку. Новый номер версии
создаёт другую доставку. Старые approved-объекты с одним ключом трактуются как
исторические PDF; backfill и пересборка не нужны. Ссылки просмотра/скачивания
продолжают обращаться к исходным `DocumentVersionFile` с их MIME и именами;
OCR, координаты и история не переключаются на утверждённую копию.

`multipart-v2` отправляет две части (`metadata`, `file`) на
`candidate-documents-v2`: ISO-даты YYYY-MM-DD, существующая обработка
`positionUid`, бинарные байты без Base64. `Idempotency-Key` равен постоянному
ID доставки. Используются Basic/token, X-File-SHA256, X-File-Size, Accept JSON
и точный Content-Length полного multipart. `StorageService.openRead` → async
iterator (буфер 64 КиБ) → Node HTTP(S) `pipeline` поддерживает backpressure и
общий AbortSignal. Файл и multipart не собираются в Buffer/Blob. Применён Node
HTTP(S), поэтому требование fetch `duplex: "half"` здесь не возникает.
Хеш/размер проверяются при передаче до завершающего разделителя; ETag не
используется. При ошибках/отмене/раннем ответе потоки закрываются.

`SENT` для v2 требует HTTP 201 с duplicate=false или 200 с duplicate=true,
полной JSON-квитанции с непустыми UUID receipt/candidate/file, совпадающих
ID доставки, documentUid, SHA-256, размера, MIME, безопасного имени и
корректной даты period. candidateUid не сравнивается с chatUid. В диагностике
остаются HTTP-статус, receiptId, duplicate, success и безопасный code; сырые
описания/реквизиты ответа v2 не сохраняются. Некорректная квитанция требует
ручной проверки и не вызывает автоматическую отправку.

`ERP_DOCUMENTS_V2_AUTO_RETRY=false` по умолчанию. После приёмки идемпотентности
на конкретной публикации оператор может включить `true`: сеть/timeout/обрыв и
HTTP 408/429/500/502/503/504 повторяются до пяти попыток всего с тем же ID,
exponential backoff (15–30, 30–60, 60–120, 120–240 секунд) и сохранённым
`nextAttemptAt`. FILE_STORAGE_NOT_CONFIGURED требует администратора, без автоповтора.
CAS по статусу и leaseToken исключает одновременную работу; истёкший lease
восстанавливается через тот же backoff. Исчерпание → REQUIRES_MANUAL;
разрешён ручной повтор с тем же ID без сброса счётчика. Выключение auto-retry
паркует уже запланированные повторы в REQUIRES_MANUAL. Для начальной отправки
PENDING worker остаётся включённым. Общий deadline v2 по умолчанию 300 секунд
(ERP_DOCUMENTS_V2_TIMEOUT_MS, 60–600 секунд), lease = deadline + 60 секунд;
v1 сохраняет HTTP timeout 60 секунд / lease 180 секунд.

При зафиксированном транспорте `base64-v1` после подтверждения worker POST-ит `candidate-documents`: documentUid,
chatUid, PDF в base64 и замороженные documentFields. Например, для ИНН запрос
выглядит так (UUID чата и содержимое PDF заменены обозначениями):

```json
{
  "documentUid": "2452c57b-8c32-11eb-ba8b-00259002db81",
  "chatUid": "<UUID чата кандидата>",
  "documentFields": {
    "issueDate": "2018-12-06",
    "series": "",
    "number": "",
    "expiryDate": "",
    "issuedBy": "",
    "departmentCode": "",
    "isIdentityDocument": false,
    "lastNameLatin": "",
    "firstNameLatin": "",
    "categories": "",
    "specialMarks": "",
    "isInvalid": false,
    "valueComment": "",
    "comment": ""
  },
  "fileExtension": "pdf",
  "fileBase64": "<base64 итогового PDF>"
}
```

Только для legacy v1 любой 2xx означает доставку.
Для v1 при HTTP/сетевой ошибке или прерванной отправке результат `REQUIRES_MANUAL`;
автоматических повторов нет: legacy-контракт не гарантирует идемпотентность.
Проверяющий с правом 20006 использует «Отправить в ERP» и видит историю попыток.
Принятый документ остаётся принятым независимо от доставки ERP.

Каждая новая попытка сохраняет HTTP-статус (`httpStatus`) и текст ответа 1С
(`responseBody`) в `erp_document_attempts`; эти данные доступны в API версии
документа и в истории отправок на экране проверки. Записываются успешные ответы,
отказы и пустые ответы. Чтение ограничено 16 КиБ и 5 секундами; усечение отмечается
`responseTruncated`, ошибка чтения — `responseReadError`. Ошибка чтения тела не
меняет уже полученный HTTP-статус и не вызывает повторную отправку. Учётные данные,
токены и содержимое файлов в ответах маскируются; сырые ответы не попадают в журналы
или аудит. В аудит записываются статус HTTP и признаки неполной диагностики.
Для старых попыток ответ недоступен (`null`): миграция не восстанавливает уже
отброшенные данные. Перед выкладкой требуется миграция `0011_erp_delivery_responses`.

Для загрузок только с `code_1c` состояние `WAITING_CONTRACT`: текущая ERP-ручка
принимает только chatUid. Код сотрудника не подставляется вместо UUID чата.

`PUT /api/internal/edo/v1/candidate-chats/{chatUuid}/employee-link` с `{code1c}`
идемпотентно связывает документы с сотрудником; другая связь — 409. ЛК пишет
код и outbox в одной транзакции до редиректа на регистрацию. Worker доставляет
связь независимо от браузера, восстанавливает прерванные отправки и исторические
связи. EDO может получить связь до первого документа; документы затем доступны
как по чату, так и по коду сотрудника.

## Развёртывание и контракты

EDO: `pnpm db:migrate` применяет все ожидающие миграции только к БД edo,
включая `0011_erp_delivery_responses` и `0016_approved_artifact_transport`.
Изменений публичного REST/OpenAPI в этапе v2 нет; генерация клиента не требуется.
ЛК: миграция `next/src/Integrations/Edo/Entities/migrations/20261013120000.php`
обнаруживается штатным доменным pipeline `next` и создаёт только
`sps_next.edo_candidate_link_outbox`. Корневой `db/migrations` для этой интеграции
не используется. Миграция требует подключение к `sps_next`; она не переносит
данные и не меняет существующие таблицы чатов или общий `queue_outbox`.

Chat-server сохраняет прежние `DB_NAME` и подключение к таблицам чатов. Его
`DB_USER` нужны `SELECT`, `INSERT`, `UPDATE` только на
`sps_next.edo_candidate_link_outbox` дополнительно к существующим правам.
Обе схемы находятся на одном MariaDB-сервере: обновление чата в старой схеме и
запись outbox в `sps_next` выполняются одной транзакцией InnoDB.
Порядок перехода: внутренний API чатов PHP → EDO → public_next → удаление
документного посредника surveys. Старые `/surveys-service/api/candidate-documents/*`
не поддерживаются: нужно обновить вкладку или мобильное приложение. Миграции
документов не требуются, существующий outbox chat-server сохраняется.

В API-образе `/app/.cache/document-uploads` остаётся закрытой директорией для `node`.
Обновление контрактов выполняется без запуска surveys:

```sh
# EDO
pnpm --filter @edo/lk-client generate
pnpm api:generate
# LK/public_next
node scripts/sync-edo-spec.mjs /path/to/edo/apps/api/openapi.json
yarn api:generate:edo
```

Пользовательский вход/refresh/logout обслуживает auth-service по `/api/auth/v1/*`.
EDO проверяет единый JWT локально (HS256, `iss=lk-auth-service`, обязательный `exp`).
Секрет EDO `JWT_SECRET` совпадает с `AUTH_JWT_SECRET` в конфигурации ЛК, который
передаётся auth-service как `JWT_SECRET`. Refresh остаётся в HttpOnly Secure cookie,
access JWT и документные доступы — только в памяти. Нужны разрешённые origins
EDO/ЛК, credentials для refresh и браузерный доступ к публичному адресу EDO.

`GET /api/candidate-documents/my/chat` использует `code_1c` проверенного JWT;
административные права ЭДО для собственных документов не нужны.
Если в LK для сотрудника ещё нет связи с чатом, собственные документы ищутся и
загружаются по `code_1c`; сервер получает должность и профиль через ERP Candidate
по параметру `code1c`, передавая значение `code_1c` проверенного JWT. Локальная
запись `lkEmployee` для этого пути не требуется. Если `candidate.uuid` ответа
пуст, `chatUuid` в контексте равен `null`; непустой UUID чата принимается только после проверки связи в ЛК.
Гостевые `/api/candidate-documents/by-chat/{chatUuid}/*` сохраняют существующую
модель доступа по закрытой ссылке чата. Сервисные токены, access JWT, upload grant
и SSE grant имеют разные назначения и не заменяют друг друга.

Проверка независимости: заблокировать обращения к surveys, открыть документы в
кандидатском чате, отправить комплект, вернуть его в EDO, исправить и повторить
отправку; проверить SSE, доставку ERP, employee-link и backfill. Экран адаптации
по-прежнему требует surveys, самостоятельная панель документов — нет.

## Отправка и решение проверяющего

Версия и сводка документа возвращают `submittedAt`, `reviewedAt`, `reviewedBy`. Время — UTC ISO 8601 с `Z`, неизвестные исторические значения — null. `submittedAt` фиксируется при успешном завершении загрузки; резервирование и неудачная загрузка датой отправки не считаются. `reviewedAt`/`reviewedBy` записываются только при подтверждении или возврате, в той же транзакции со статусом и аудитом. Открытие и редактирование реквизитов не являются решением.

`reviewedBy` — UUID из проверенного JWT; `reviewedByName` в деталях версии берётся из локальной LK-проекции при однозначном совпадении UUID. При неизвестном имени UI показывает UUID. Повторная отправка создаёт новую версию с новой датой отправки и пустой проверкой; старые сведения сохраняются в истории. Повтор того же idempotency key не меняет время.

Миграция 0012 восстанавливает даты только из однозначного аудита `DOCUMENT_UPLOADED`/`DOCUMENT_RETURNED` с номером версии и существующих `approvedAt`/`approvedBy`. Внешний OCR добавляет отдельные `ocrFields`; они доступны даже для необязательных полей и не добавляются автоматически в ERP-документ. Сводки/SSE включают `ocrStatus` и `ocrErrorCode`, чтобы открытое рабочее место обновлялось при завершении распознавания.
