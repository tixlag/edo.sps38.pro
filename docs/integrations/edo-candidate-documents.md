# Документы кандидата из чата ЛК

## Граница интеграции

ЛК проверяет доступ кандидата к чату и передаёт в EDO исходные файлы одного
документа. EDO хранит данные по `chatUuid`, выполняет асинхронный OCR и позволяет
проверяющему исправить и подтвердить документ. Подтверждение документа не запускает
трудоустройство и не создаёт физлицо, сотрудника или `code_1c`.

Внешний OCR пока **не подключён**: URL, авторизация и контракт будут предоставлены
отдельно. `OcrService.recognize()` — внутренний интерфейс адаптера, а не формат
запроса к внешнему сервису. Он принимает код документа и упорядоченные файлы с
краткоживущими подписанными S3-ссылками, MIME и количеством страниц. Адаптер
передаёт изображения/PDF по реальному контракту; если OCR принимает только
изображения, преобразование страниц PDF реализуется внутри этого адаптера.

`OCR_MODE=disabled` по умолчанию: загрузка возвращает `503 OCR_NOT_CONFIGURED`.
Для локальной проверки можно явно поставить `OCR_MODE=stub` при
`NODE_ENV=development` или `test`. Заглушка возвращает фиксированные синтетические
поля, `ocrSource=STUB` и `raw.synthetic=true`; она не оценивает содержимое, качество
или соответствие типа. В production заглушка запрещена, в том числе при запуске.
Функциональность реального OCR включается после реализации и подключения адаптера.

## Настройки

Корневой `.env`:

- `EDO_LK_INTERNAL_TOKEN`: отдельный входящий серверный токен ЛК → EDO.
  Не путать с `LK_EDO_INTERNAL_TOKEN`, который используется в обратном направлении.
- `OCR_MODE=disabled|stub`, `OCR_WORKER_ENABLED=true|false`.
- `EDO_OCR_QUEUE=edo.ocr`, `LK_EVENTS_EXCHANGE=lk.events`, общий `RABBITMQ_URL`.
- `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`.

Бакет должен существовать и быть закрытым. API не создаёт бакет и не меняет его
политику доступа. Для moto оператор может создать бакет через совместимый S3-клиент;
для MinIO предусмотрен compose-профиль `minio` с `createbucket`.

EDO создаёт только свои очереди `edo.ocr` и `edo.ocr.dlq` и binding
`edo.ocr.requested.v1` к существующему `lk.events`. Обменник ЛК не переобъявляется.
Оператор расширяет разрешения серверного пользователя RabbitMQ: configure на
`edo\.ocr.*`, write на `lk\.events` и `edo\.ocr.*`, read на `lk\.events` и
`edo\.ocr.*`, сохраняя прежние разрешения LK-синхронизации. При другом имени очереди
правила меняются соответственно. Никогда не удалять рабочие очереди: глубина
очередей и сообщения в `.dlq` проверяются средствами оператора RabbitMQ.

`OCR_WORKER_ENABLED=false` отключает обработчик, публикацию outbox и фоновую
очистку. Этот режим используется при экспорте OpenAPI и управляемых тестах.

## Загрузка и получение результата

Все серверные ручки требуют `Authorization: Bearer <EDO_LK_INTERNAL_TOKEN>`.
Пользовательский JWT не заменяет этот токен; кандидат не вызывает API напрямую.

`POST /api/internal/edo/v1/candidate-chats/{chatUuid}/documents`:

- `Content-Type: multipart/form-data`.
- Обязательный `Idempotency-Key`: 1–128 печатных ASCII-символов без пробелов.
- `documentTypeCode`: существующий код `DocumentType`.
- `files[]`: 1–10 изображений JPEG/PNG/WebP или PDF; смешанный комплект допустим.
- `locationId`: необязательный положительный ID активного объекта из проекции ЛК.

Один комплект представляет **один документ**, файлы упорядочены по multipart,
страницы PDF — в исходном порядке. Каждый файл ограничен 10 МиБ, весь комплект —
50 МиБ и 100 страницами; изображения — 40 мегапикселями. MIME и расширение
недостоверны: тип определяется по содержимому. Повреждённые, пустые файлы,
анимированные изображения и зашифрованные PDF отклоняются.

Пример (токен берётся из окружения вызывающего сервера):

```sh
curl -X POST "$EDO_BASE_URL/api/internal/edo/v1/candidate-chats/$CHAT_UUID/documents" \
  -H "Authorization: Bearer $EDO_LK_INTERNAL_TOKEN" \
  -H "Idempotency-Key: $DOCUMENT_BUNDLE_ID" \
  -F 'documentTypeCode=PASSPORT' \
  -F 'files[]=@front.jpg' \
  -F 'files[]=@other-pages.pdf'
```

`202` возвращает `{candidateId, documentId, version, jobId}` после сохранения файлов
и фиксации задания/outbox. Один документ каждого типа на чат; новый комплект —
новая версия. Повтор идентичного запроса с тем же ключом возвращает прежние ID.
Ключи чувствительны к регистру. Изменение файлов, порядка, имён, типа или явно
переданного объекта с тем же ключом — `409`. Если загрузка ещё идёт, повтор
получает `409` и может быть повторён позже. После `UPLOAD_FAILED` нужен новый ключ.

`GET /api/internal/edo/v1/candidate-chats/{chatUuid}/documents/{documentId}/versions/{version}`
возвращает состояние задания, исходные/текущие поля, `raw`, источники и причины
отказа. Документ другого чата возвращает `404`.

Состояния задания: `UPLOADING → QUEUED → RUNNING → SUCCEEDED|REJECTED|FAILED`.

- `SUCCEEDED`: версия переходит в `IN_REVIEW`, оригиналы сохраняются.
- `REJECTED`: OCR сообщил `DOCUMENT_TYPE_MISMATCH` и/или `POOR_IMAGE_QUALITY`.
  Причина содержит `message`, необязательные `fileOrdinal` (с нуля) и `pageNumber`
  (с единицы внутри файла, включая PDF). Удаляется весь отклонённый комплект;
  статус/причины/raw остаются, `cleanupPending` показывает незавершённую очистку.
- `FAILED`: техническая ошибка, не отказ по качеству. `errorCode` содержит безопасную
  категорию. После ошибки OCR оригиналы сохраняются для диагностики и новой загрузки;
  неполная загрузка `UPLOAD_FAILED` очищается.

Некорректный запрос/тип/объект/PDF — `400`, авторизация — `401`, лимиты — `413`,
формат — `415`, конфликт — `409`, недоступный OCR или сбой загрузки — `503`.
Ошибки содержат `statusCode`, `message`, `correlationId`, `path`.

## Проверка в EDO

JWT и права проверяются на сервере: чтение требует `EDO_ACCESS` (20000), изменения
и подтверждение — `DOCUMENT_REVIEW` (20002). `FULL_ACCESS` даёт эти права по
существующим правилам. Право `ACCESS_ALL_LOCATIONS` само по себе не даёт права
на действия. Список и карточки фильтруются по объекту; кандидат без объекта
доступен только пользователям с доступом ко всем объектам.

- `GET /api/v1/document-types`: доступные коды.
- `GET /api/v1/candidates?limit=50&cursor=...`: список кандидатов, `nextCursor`.
- `GET /api/v1/candidates/{candidateId}/documents`: документы и текущие версии.
- `GET /api/v1/documents/{documentId}/versions/{version}`: файлы, поля и результат.
- `GET /api/v1/documents/{documentId}/versions/{version}/files/{fileId}/download`:
  `{url, expiresAt}`, ссылка действует 5 минут. Отклонённые/неполные файлы недоступны
  сразу после фиксации отказа, даже если физическое удаление ещё ожидает S3.
  Уже выданная ссылка действует до истечения срока или физического удаления файла.
- `PATCH /api/v1/documents/{documentId}/versions/{version}/fields`:
  `{revision, fields: {fieldName: "value" | null}}`.
- `POST /api/v1/documents/{documentId}/versions/{version}/approve`: `{revision}`.

Правки/подтверждение разрешены только для текущей версии в `IN_REVIEW`.
Исправления могут дополнить отсутствующее поле; `null` очищает значение. Ограничения:
200 полей, имя 1–128 символов, значение до 16384 символов. Имена чувствительны к
регистру. `originalValue` и `raw` неизменны; ручное значение и автор правки отдельны.
Каждая правка/подтверждение увеличивает `revision`, устаревшая ревизия/версия — `409`.
Подтверждение устанавливает `APPROVED`, `approvedAt`, `approvedBy`. Новая версия
снова проходит OCR/проверку, прежние данные и аудит сохраняются.

`PUT /api/internal/edo/v1/candidate-chats/{chatUuid}/employee-link` с `{code1c}`
сохраняет явную связь, даже если физлицо ещё не появилось в проекции сотрудников.
Повтор той же связи идемпотентен; замена другим кодом — `409`. EDO не сопоставляет
людей по ФИО и не создаёт сотрудников автоматически.
`GET /api/v1/employees/{employeeId}/documents` учитывает собственные документы дела
и документы кандидатов с тем же явно связанным `lkEmployeeCode1c`, с проверкой
доступа к делу **и** документам. При привязке файлы/история не переносятся.

## Доставка, восстановление и очистка

Метаданные версии и пути всех файлов фиксируются до записи в S3: неполная запись
не оставляет неизвестных системе объектов. Старт/завершение загрузки и критические
изменения пишутся атомарно с аудитом. Задание и outbox фиксируются одной транзакцией.
Публикация требует publisher confirm и отсутствия correlated mandatory return.
После сбоя публикации outbox остаётся в MariaDB и повторяется.

Обработчик имеет ограниченный prefetch, lease с токеном и сроком; повторы/поздние
ответы не перезаписывают сохранённый результат или новую версию. Сбой процесса
восстанавливается по истёкшему lease. Технические ошибки OCR повторяются до пяти
попыток с задержками 5/10/20/40 секунд; вызов адаптера ограничен 60 секундами.
Неверный контракт завершает задание с `OCR_CONTRACT_INVALID` без бессмысленных
повторов. Недоступность MariaDB сохраняет исходное сообщение и откладывает requeue.
Некорректные сообщения уходят в OCR `.dlq`.

S3-загрузка ограничена 120 секундами; незавершённые DB-задания восстанавливаются
через 10 минут. Очистка отклонённых/неполных объектов повторяется при ошибках S3.
Временные локальные файлы находятся только в `.cache/document-uploads`, удаляются
после запроса; остатки после падения очищаются через час. Outbox повторно публикует
зависшие `QUEUED` задания через две минуты; это также восстанавливает потерянную
доставку, пока MariaDB и исходные файлы сохраняются.

## Проверки

Миграции применяются через `pnpm db:migrate` только к БД `edo`.
`pnpm api:generate` обновляет OpenAPI и Orval-клиент.

Сквозной набор `apps/api/test/documents-infra.spec.ts` требует **отдельных** тестовых
MariaDB, RabbitMQ и moto; без явных переменных пропускается и никогда не использует
основные DSN. Допустимы только loopback MariaDB :3307/:3308 (БД `edo`), AMQP
:5673/:5675 и S3 :5001. CI создаёт эти одноразовые сервисы и запрещает пропуски.

```sh
EDO_TEST_DATABASE_URL=mysql://edo:edo@127.0.0.1:3308/edo \
EDO_TEST_RABBITMQ_URL=amqp://edo:edo@127.0.0.1:5673/ \
EDO_TEST_S3_ENDPOINT=http://127.0.0.1:5001 \
pnpm --filter @edo/api exec vitest run test/documents-infra.spec.ts
```
