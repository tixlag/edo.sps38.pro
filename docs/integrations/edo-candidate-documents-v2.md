# EDO → 1С: документы кандидатов, API v2

Дата контракта: 2026-10-22. Основной контракт для разработки отправителя EDO.
Реализация подготовлена в расширении ERPDev.PROFI. Публикация и приемка в работающей 1С не выполнены.

## Принятые решения

- Новый маршрут: `POST /ERP/hs/api/candidate-documents-v2`.
- Старый `candidate-documents` сохраняет JSON/Base64-контракт.
- Ровно один исходный файл: JPEG, PNG, WebP или PDF. Конвертации, ресайза, перепаковки и перекодирования нет.
- По уточнению владельца задачи файлы v2 должны сохраняться штатной БСП в дисковых томах. Если БСП выбирает
  хранение в информационной базе, v2 возвращает `503 FILE_STORAGE_NOT_CONFIGURED` до добавления вложения.
  Общие настройки хранения автоматически не изменяются. Метаданные документов и реестр доставок хранятся в ИБ.
- Принято ограничение: при откате или аварии записи в томе могут остаться осиротевшие байты.
  Автоматическая компенсирующая очистка постоянных томов не выполняется. Это не дает права вернуть успешную
  квитанцию: документ, объект вложения и реестр доставки должны быть зафиксированы одной транзакцией ИБ.
- Исходное `filename` используется для проверки расширения. В 1С сохраняется безопасное имя `document.<ext>`;
  произвольное имя отправителя не попадает в квитанцию и сообщения БСП.

## Авторизация и заголовки

Сохраняются Basic-аутентификация публикации и входящий токен `HTTP_IN_API` из заголовка `token`.
Токен не переносится в JSON. Передача — через HTTPS на внешней стороне публикации.

| Заголовок | Требование |
|---|---|
| Authorization | `Basic <existing credentials>`; обработка на уровне публикации |
| token | Действующий API token |
| Idempotency-Key | Обязательный, 1–128 символов ASCII с кодами 33–126; пробелы и управляющие символы запрещены |
| X-File-SHA256 | Обязательный SHA-256 исходных бинарных байтов: ровно 64 символа `0-9a-f` |
| X-File-Size | Обязательное положительное десятичное целое: размер именно файла в байтах |
| Content-Type | `multipart/form-data; boundary=<boundary>`; кавычки вокруг boundary поддерживаются |
| Accept | `application/json` |

Имена HTTP-заголовков нечувствительны к регистру. Значение ключа доставки сохраняется без обрезки и изменения
регистра; ключи `Delivery-A` и `delivery-a` различны. Сжатое тело `Content-Encoding` не принимается.
Для chunked-запроса отсутствие Content-Length допустимо: ограничивается фактическое количество прочитанных байтов.
При наличии Content-Length значение дополнительно сверяется с прочитанной длиной.

## Multipart

Ровно две именованные части, в любом порядке: `metadata` и `file`. Дополнительные и повторные части запрещены.
Разделители — CRLF. Preamble, epilogue, LF вместо CRLF, вложенный multipart, Content-Transfer-Encoding,
`filename*` и дополнительные заголовки частей этим контрактом не поддерживаются.

```http
Content-Type: multipart/form-data; boundary="EDO-boundary-123"

--EDO-boundary-123\r\n
Content-Disposition: form-data; name="metadata"\r\n
Content-Type: application/json; charset=utf-8\r\n
\r\n
{"documentUid":"2452c57b-8c32-11eb-ba8b-00259002db81","chatUid":"<chat UUID>","documentFields":{"series":"","number":"","issueDate":"2020-01-15","isIdentityDocument":false}}\r\n
--EDO-boundary-123\r\n
Content-Disposition: form-data; name="file"; filename="document.jpg"\r\n
Content-Type: image/jpeg\r\n
\r\n
<исходные бинарные байты>\r\n
--EDO-boundary-123--\r\n
```

В примере `\r\n` обозначает реальные байты CRLF, а не четыре печатных символа.
Финальный CRLF после закрывающей границы необязателен. Boundary: 1–70 ASCII-символов по набору MIME boundary;
пробел разрешен только внутри quoted boundary, завершающий пробел запрещен. Отправитель выбирает boundary,
который не встречается в данных как полный MIME-разделитель.

`metadata` — JSON-объект в UTF-8. Допустимы только `documentUid`, `chatUid`, `documentFields`.
`documentUid` и `chatUid` обязательны. `documentFields` можно не передавать либо передать `{}`.
`fileBase64` и `fileExtension` в v2 запрещены. Кандидат определяется существующим способом по `УидЧатаЛК`;
новое требование проверять UUID у chatUid не вводилось.

Поля documentFields и проверки переиспользуются из действующего API:

| Поле | Тип и предел |
|---|---|
| series | Строка, 14; типовая проверка серии для вида документа |
| number | Строка, 16; типовая проверка номера для вида документа |
| issueDate, expiryDate | Строка `YYYY-MM-DD` либо пустая строка по прежним правилам |
| issuedBy | Строка, 200 |
| departmentCode | Строка, 15 |
| isIdentityDocument | Булево |
| lastNameLatin, firstNameLatin | Строка, 50 |
| categories, specialMarks | Строка, 500 |
| positionUid | UUID должности либо пустая строка |
| isInvalid | Булево |
| valueComment | Строка, 200 |
| comment | Строка, 500 |

Неизвестные поля и неверные типы отклоняются; null не заменяет строку или булево.
Сохраняются прежние правила обязательности, удостоверения личности, существования кандидата/вида документа,
папки `ER-00000001`, а также запрет замещения записи за текущую дату.

## Форматы и ограничения

| Формат | MIME | Расширение отправителя | Расширение в 1С |
|---|---|---|---|
| JPEG | image/jpeg | jpg, jpeg | jpg |
| PNG | image/png | png | png |
| WebP | image/webp | webp | webp |
| PDF | application/pdf | pdf | pdf |

Регистр расширения несущественен. MIME, расширение и обнаруженная структура должны соответствовать друг другу.
Переименование `.jpeg` → `.jpg` меняет только расширение, байты файла остаются прежними.
Путь вместо имени, пустое имя и имя длиннее 255 символов запрещены.

- Файл: от 1 до **104857600** байт, включая границу 100 МиБ.
- Metadata: от 1 до **262144** байт.
- Заголовки каждой части вместе с CRLFCRLF: не более **8192** байт.
- Полное HTTP-тело: не более **105136128** байт = 100 МиБ + 256 КиБ + 16 КиБ обвязки.
  Общий лимит имеет приоритет: максимально длинные заголовки не гарантируют возможность заполнить обе части до предела.
- Проверяются фактическая длина и SHA-256 файла до добавления вложения.

Проверки содержимого: JPEG SOI/EOI, сегменты и наличие размеров/SOS; PNG signature, IHDR, границы чанков,
CRC32, IDAT и IEND; WebP RIFF/WEBP, заявленная длина, границы/выравнивание чанков и сигнатуры VP8/VP8L;
PDF — сигнатура и чтение штатным `ДокументPDF` с непустым набором страниц. Зашифрованный PDF, требующий пароля,
может быть отклонен с 422. Проверка изображений является структурной и не доказывает декодируемость каждого пикселя
или каждого кадра анимации WebP. Антивирусная проверка в эту реализацию не включена.

## Ответы

Первое сохранение — **201**:

```json
{
  "success": true,
  "receiptId": "90000000-0000-0000-0000-000000000001",
  "deliveryId": "edo-delivery-example-001",
  "duplicate": false,
  "candidateUid": "10000000-0000-0000-0000-000000000001",
  "documentUid": "2452c57b-8c32-11eb-ba8b-00259002db81",
  "fileUid": "20000000-0000-0000-0000-000000000001",
  "period": "2026-10-22",
  "fileName": "document.jpg",
  "mimeType": "image/jpeg",
  "fileSha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "fileSize": 123456
}
```

UUID и хеш в примере иллюстративные. Успешный повтор — **200**, те же значения полей, но `duplicate: true`.
`documentUid` обозначает вид документа; сам документ — запись регистра с ключом кандидат/вид/period.
`period` — дата сеанса 1С на момент первоначального создания. Даты реестра начала/завершения записываются в UTC.
Часовой пояс веб-сервера не меняет period.

Ошибка:

```json
{"success":false,"code":"FILE_HASH_MISMATCH","description":"Контрольная сумма файла не совпадает."}
```

| HTTP | Основные code |
|---|---|
| 400 | INVALID_IDEMPOTENCY_KEY, INVALID_FILE_HASH, INVALID_FILE_SIZE, INVALID_CONTENT_LENGTH, INVALID_BOUNDARY, INVALID_MULTIPART, EMPTY_PART, INVALID_METADATA, INVALID_DOCUMENT_FIELDS, INVALID_FILE_NAME, INCOMPLETE_REQUEST |
| 401 | UNAUTHORIZED |
| 403 | FORBIDDEN |
| 404 | CANDIDATE_OR_DOCUMENT_NOT_FOUND |
| 409 | IDEMPOTENCY_CONFLICT, DOCUMENT_ALREADY_EXISTS, DOCUMENT_CONFLICT |
| 413 | REQUEST_TOO_LARGE, FILE_TOO_LARGE, PART_TOO_LARGE, PART_HEADERS_TOO_LARGE |
| 415 | UNSUPPORTED_MEDIA_TYPE, UNSUPPORTED_CONTENT_ENCODING, INVALID_METADATA_TYPE, UNSUPPORTED_FILE_FORMAT, FILE_TYPE_MISMATCH |
| 422 | FILE_SIZE_MISMATCH, FILE_HASH_MISMATCH, INVALID_FILE_CONTENT |
| 500 | INTERNAL_ERROR |
| 503 | DELIVERY_BUSY, DELIVERY_NOT_COMPLETED, FILE_STORAGE_NOT_CONFIGURED |

У 503 установлен Retry-After: 5. Настройку томов при FILE_STORAGE_NOT_CONFIGURED должен проверить администратор;
постоянные частые повторы не устраняют ошибку настройки. Ответы Basic-аутентификации, proxy и платформы до входа
в обработчик могут иметь собственный формат; EDO обязан учитывать HTTP-статус и не считать HTML успешной квитанцией.

## Идемпотентность и сбои

Непериодический независимый регистр `PROFI_ДоставкиДокументовКандидатовEDO` имеет одно измерение:
SHA-256 точных UTF-8 байтов Idempotency-Key. Это исключает зависимость уникальности ASCII-ключа от регистронезависимого
сравнения строк СУБД. Исходный ключ также хранится и сравнивается. Хранятся отпечаток metadata, MIME, размер,
SHA-256 файла, candidate/kind/file, дата документа, receiptId, состояние Completed, даты и JSON успешной квитанции.
Исходные документы и metadata с персональными реквизитами в этом реестре не дублируются.

Metadata нормализуется: устойчивый порядок верхних и вложенных ключей; documentUid и positionUid в нижнем регистре;
chatUid обрезается по тем же правилам, что поиск кандидата; отсутствие documentFields равно `{}`.
Значения текстовых реквизитов не изменяются. Отключенная дата, пустое значение и отсутствующее поле не объявляются
взаимозаменяемыми: отправитель должен повторять те же значения. Boundary и имя файла в отпечаток не входят.

| Ситуация | Результат |
|---|---|
| Новый ключ и новый документ | 201; Completed фиксируется вместе с документом |
| Тот же ключ, metadata/MIME/размер/SHA-256 прежние | 200 и исходная квитанция; нового файла нет |
| Тот же ключ, изменены сравниваемые данные | 409 IDEMPOTENCY_CONFLICT |
| Другой ключ, тот же вид документа у кандидата за этот день | 409 DOCUMENT_ALREADY_EXISTS |
| Повтор через несколько дней | 200 с первоначальным period/receiptId/fileUid |
| Два одновременных запроса одного ключа | Исключительная блокировка ключа; второй читает результат первого либо получает 503 |
| Разные ключи одного кандидата | Дополнительно действует прежняя блокировка всех видов документов кандидата за день |
| Ошибка до сохранения / ошибка вложения / ошибка записи регистра | Нет успешной доставки и документа после отката |
| Потеря ответа после фиксации | Повтор с исходным ключом возвращает 200 |

Порядок блокировок: доставка → документы кандидата за день → операции штатной БСП.
Вложенные транзакции БСП и общего бизнес-метода не фиксируют внешнюю транзакцию доставки.
Квитанция возвращается только после внешнего commit. Реестр нельзя очищать по возрасту без отдельного изменения
контракта, иначе долговременная идемпотентность будет потеряна. Роль ручного изменения предназначена только
для административного восстановления и автоматически никому не назначается.

Физическая запись тома не участвует в транзакции СУБД. По уточнению владельца задачи остатки после ошибки,
аварийного завершения или обрыва до commit принимаются как ограничение; код не удаляет постоянные файлы наугад.
Повтор может создать новый физический остаток, но итоговый документ, зарегистрированное вложение и квитанция
должны быть единственными. Удаление файлов, на которые ссылается успешная доставка, запрещено.

## curl

Переменные EDO_BASIC и EDO_TOKEN должны быть заданы безопасным способом вне команды. Их значения не записываются
в документацию, файлы исходников и диагностический вывод. Не используйте `curl -v` с рабочими учетными данными.
Примеры для shell Linux; metadata.json содержит только согласованные metadata.

JPEG:

```sh
FILE=document.jpg
HASH=$(sha256sum "$FILE" | cut -d' ' -f1)
SIZE=$(wc -c < "$FILE" | tr -d ' ')
curl --fail-with-body --request POST "$EDO_BASE/ERP/hs/api/candidate-documents-v2" \
  --header "Authorization: Basic $EDO_BASIC" --header "token: $EDO_TOKEN" \
  --header 'Idempotency-Key: edo-delivery-example-001' \
  --header "X-File-SHA256: $HASH" --header "X-File-Size: $SIZE" --header 'Accept: application/json' \
  --form 'metadata=@metadata.json;type=application/json;charset=utf-8' \
  --form "file=@$FILE;type=image/jpeg"
```

PDF:

```sh
FILE=document.pdf
HASH=$(sha256sum "$FILE" | cut -d' ' -f1)
SIZE=$(wc -c < "$FILE" | tr -d ' ')
curl --fail-with-body --request POST "$EDO_BASE/ERP/hs/api/candidate-documents-v2" \
  --header "Authorization: Basic $EDO_BASIC" --header "token: $EDO_TOKEN" \
  --header 'Idempotency-Key: edo-delivery-example-002' \
  --header "X-File-SHA256: $HASH" --header "X-File-Size: $SIZE" --header 'Accept: application/json' \
  --form 'metadata=@metadata.json;type=application/json;charset=utf-8' \
  --form "file=@$FILE;type=application/pdf"
```

Content-Type всего запроса вручную не задается: curl сам формирует boundary.
Для повторной доставки сохраняйте delivery ID и исходные байты, metadata, MIME, размер и хеш в EDO.
При сетевом обрыве и 503 повторяйте с тем же ключом; конфликт 409 не обходите генерацией нового ключа.

## Память, диск, платформа и публикация

В исходниках используется `HTTPСервисЗапрос.ПолучитьТелоКакПоток()`. Собственный код читает по 64 КиБ,
ограничивает суммарную длину и сохраняет тело во временный файл, затем извлекает отдельный файл на диск.
Поиск границ работает с небольшими hex-представлениями блоков; весь файл в строку не преобразуется.
UTF-8 декодируется только у metadata и ограниченных заголовков.

Для штатного `РаботаСФайламиСлужебныйВызовСервера.ДобавитьФайл()` требуется материализовать извлеченный файл
как `ДвоичныеДанные` и поместить во временное хранилище. Поэтому процесс в целом **не полностью потоковый**.
Собственная обработка тела имеет постоянный размер рабочего блока; этап БСП ограничен размером одного файла,
но может создавать внутренние копии. Штатный парсер PDF также расходует память, точный пик не измерен.
Временное место на один запрос — примерно два размера файла плюс metadata/обвязка, до 201 МиБ с запасом;
для N параллельных запросов место и память планируются с учетом N. Встроенная буферизация HTTP платформы,
БСП и декодера PDF не подтверждена измерением. Нагрузочная приемка 100 МиБ обязательна до включения.

Обычные ошибки удаляют оба временных файла и закрывают потоки. После аварийного завершения процесса
очистка ОС/платформы требует отдельного контроля. Не добавляйте очистку томов с документами по маске возраста.

В EDT совместимость расширения — 8.3.27; локально обнаружены дистрибутивы 8.3.27.1719/2130.
Фактический runtime сервера публикации не установлен по этим данным. Проверены справочные сигнатуры потоков,
буферов, SHA-256, ДокументPDF и используемых методов БСП. Настройки действующего IIS/Apache/nginx,
reverse proxy, памяти рабочего процесса и таймаутов **не прочитаны и не изменены**.

Требуемый лимит полного тела на каждом уровне — не меньше 105136128 байт. Примеры для администратора,
применяемые только к новому пути с сохранением существующей схемы публикации:

- nginx: `client_max_body_size 105136128;` в location нового endpoint;
- IIS requestFiltering: `requestLimits maxAllowedContentLength="105136128"` в допустимой области нового пути;
- Apache: `LimitRequestBody 105136128` для соответствующего Location.

Это шаблоны, а не подтверждение действующих конфигураций. Проверьте наследование/блокировку секций IIS,
буферизацию, таймауты загрузки, свободное место, квоты, лимиты памяти 1С и число одновременных загрузок.
Нельзя менять общие лимиты других HTTP-сервисов без отдельного решения. Ошибки прокси 413 могут иметь собственное тело.

MIME и SHA-256 сохраняются явно в реестре доставки: они не восстанавливаются впоследствии только по расширению.
Нельзя использовать хеш Base64 или повторно сохраненного изображения вместо хеша переданных байтов.

## WebP и открытие существующими средствами

Статически прослежен маршрут формы ДокументыКандидатов.ФормаЗаписи:
`ФайлОткрытие` → `РаботаСФайламиКлиент.ДанныеФайла` → `ОткрытьФайл` → получение файла и запуск приложения
либо браузерный путь открытия без расширения. Это сохраняет возможность получения исходного файла.
В найденном стандартном списке изображений БСП WebP не указан; встроенный предпросмотр WebP не подтвержден.
Сохранение, скачивание и внешний просмотр конкретными клиентами требуют запуска 1С.

Совместимое решение: скачивать исходный `.webp` и открывать браузером или приложением с поддержкой WebP.
Бесшумное преобразование в PNG/PDF отсутствует. Если обязателен встроенный просмотр, EDO может отдельно
предоставлять JPEG/PNG с новым согласованным идентификатором доставки; менять байты успешной доставки нельзя.
Не включайте WebP в продуктивный поток до успешной приемки сохранения и скачивания в используемых клиентах.

## Безопасное включение и приемка

1. Применить расширение только на согласованном тестовом стенде; продуктивная ИБ в ходе разработки не изменяется.
2. Проверить папку ER-00000001, доступность томов и выбор БСП для всех четырех расширений и размеров вплоть до 100 МиБ.
   Если смешанное хранение направляет маленькие файлы в ИБ, согласовать настройку томов с администратором;
   код не меняет ее автоматически и возвращает 503.
3. Проверить запреты/разрешения расширений БСП и служебные права текущей учетной записи.
4. Новую роль `PROFI_APIПриемДокументовКандидатовV2` назначает администратор целевой интеграционной учетной записи.
   Старые роли не изменены. Базовые новые роли: `PROFI_ЧтениеДоставокДокументовEDO`,
   `PROFI_ИзменениеДоставокДокументовEDO`; автоматически пользователям не назначаются.
5. Проверить лимиты и таймауты всех уровней публикации, журналирование без персональных данных и секретов.
6. Запустить самопроверку multipart/форматов из `src/ERPDev.PROFI/tests/edo-candidate-documents-v2`.
7. Провести интеграционные сценарии ниже с проверкой фактических данных и числа вложений.
8. Выполнить измерение памяти/диска/времени на файлах возле лимита, включая PDF; установить допустимый параллелизм.
9. Проверить старый endpoint теми же ранее принятыми JSON-запросами. Включать EDO постепенно после приемки.

Интеграционные сценарии для агента EDO и приемщика 1С:

- JPEG, PNG, PDF, WebP: 201, исходное расширение/MIME, скачанные байты и SHA-256 идентичны; нет нового PDF из изображения.
- WebP: отдельно тонкий/веб-клиент, скачивание, внешнее открытие и ограничение встроенного просмотра.
- Корректный/неизвестный/неоднозначный chatUid; существующий/удаленный вид; серия/номер/даты/типы и удостоверение личности.
- Повтор того же ключа: 200, все UUID, period, имя и хеш прежние, одна запись документа и одно итоговое вложение.
- Перестановка ключей JSON, другой boundary, перестановка частей: прежняя квитанция.
- Изменение metadata, MIME или файла с тем же ключом: 409; неправильный заявленный хеш/размер: 422 до сохранения.
- Другой ключ уже существующего вида за текущую дату: 409 DOCUMENT_ALREADY_EXISTS.
- 2–8 одновременных повторов одного ключа, разные ключи одного кандидата и существующая блокировка удостоверений личности.
- Сетевой обрыв после commit и повтор через несколько дней: 200 с исходной квитанцией.
- Ошибка записи тома, ошибка записи документа/реестра, таймаут блокировки: нет ложного Completed/2xx.
- Убийство процесса после записи тома до commit: документ и квитанция откатываются; возможный дисковый остаток допустим.
- Пустые/неизвестные/дополнительные/повторные части, LF, обрезанный запрос, неверный boundary, подмена MIME/расширения.
- Ровно 100 МиБ и 100 МиБ + 1; metadata 256 КиБ и +1; Content-Length отсутствует/неверен; фактический общий лимит.
- Проверка журналов: нет Authorization, token, значений documentFields, содержимого документа и сырых байтов.

## Состав реализации и граница проверок

- `HTTPServices/API/API.mdo`: новый URLTemplate CandidateDocumentsV2.
- `HTTPServices/API/Module.bsl`: CandidateDocumentsV2POST; прежние обработчики сохранены.
- `CommonModules/PROFI_APIДокументыКандидатовСервер/Module.bsl`: общий бизнес-метод и вход из бинарного файла;
  сигнатура СоздатьДокумент и Base64-поведение v1 сохранены.
- `CommonModules/PROFI_APIДокументыКандидатовV2Сервер/Module.bsl`: multipart, ограничения, форматы, SHA-256, реестр и квитанции.
- Новый регистр доставок, три новые роли и ссылки на них в Configuration.mdo.
- Генератор и BSL-самопроверка; двоичные фикстуры создаются отдельно и в репозиторий не включаются.

Синтаксис/метаданные/запросы/дифф проверяются статически. BSL-самопроверка и реальные HTTP-, файловые,
конкурентные, аварийные и клиентские сценарии должны быть явно отмечены как выполненные на тестовом стенде.
Наличие подготовленных фикстур или нулевых ошибок EDT не является доказательством прохождения этих сценариев.
