# Чат кандидата в EDO

Из очереди `/review` кандидат открывается по адресу
`/review/candidates/{candidateId}`. Поиск кандидатов работает независимо от
фильтров очереди и включает импортированных из ERP кандидатов без документов.
Чат объединяет ЛК, Telegram, WhatsApp и SMS. Документ открывает существующий
экран проверки; возврат в чат сохраняет его черновик. Фильтры очереди, выбранный
документ и версия сохраняются в URL.

## Границы и доступ

- Браузер обращается только к EDO: DTO → OpenAPI → Orval (`@edo/api-client`).
  Старый `GET /api/v1/candidates` сохранён; независимый каталог использует
  `GET /api/v1/candidates/catalog`.
- Чтение требует EDO ACCESS и доступа к объекту кандидата. Неизвестный объект
  недоступен пользователям с ограничением по объектам. Отправка дополнительно
  требует DOCUMENT_REVIEW / FULL_ACCESS и `code_1c` проверенного JWT.
  Поле автора из браузера не принимается.
- ERP остаётся владельцем получателей, шаблонов и транспортов Telegram,
  WhatsApp и SMS. EDO не получает ключи этих провайдеров. История включает
  сообщения кандидата и связанных физических лиц; ФИО/телефон не используются
  для автоматического объединения карточек.
- Для одного сообщения разрешён один PDF, JPEG, PNG или файл Microsoft Office
  до 10 МБ. SMS поддерживает только текст. Отсутствующий источник не скрывает
  историю остальных источников.
- Черновики и пользовательский JWT находятся только в памяти вкладки.
  При смене пользователя/выходе черновики очищаются.

## Подключение

1. Опубликовать изменения 1С: HTTPService API, общий модуль
   `PROFI_APIКоммуникацииКандидатовСервер`, регистр
   `PROFI_ОтправкиЧатаЭДО`, роль `PROFI_APIКоммуникацииЭДО` и изменения
   существующих транспортных процедур/журнала. Назначить роль служебному
   пользователю. Проверка `HTTP_IN_API` и Basic обязательны. Для файлов нужна
   существующая папка BSP `ER-00000001`.
2. Обновить chat-server ЛК с поддержкой нескольких соединений одного session
   ID. Это нужно для одновременной работы EDO, формы 1С и нескольких вкладок.
   Изменение не затрагивает атомарный employee-link outbox.
3. В серверной конфигурации EDO задать:

   ```dotenv
   ERP_COMMUNICATIONS_URL=https://api-erp.sps38.pro/ERP/hs/api/candidate-communications
   ERP_COMMUNICATIONS_TOKEN=<HTTP_IN_API token>
   ERP_USERNAME=<service account>
   ERP_PASSWORD=<service account password>
   LK_CHAT_BASE_URL=https://lk.sps38.pro:8091
   LK_PUBLIC_BASE_URL=https://lk.sps38.pro
   CANDIDATE_CATALOG_SYNC_ENABLED=true
   ```

   `LK_CHAT_BASE_URL` — существующий HTTP(S) адрес chat-server, доступный из
   API EDO. Файлы читаются через публичный nginx `LK_PUBLIC_BASE_URL`, а не
   через порт chat-server. Секреты не должны иметь префикс `VITE_`.
4. Применить миграции только к базе `edo`: `pnpm db:migrate`.
   Перегенерировать контракт при изменении endpoint: `pnpm api:generate`.
5. Запустить импорт: `pnpm --filter @edo/api candidates:sync`.
   Периодический импорт запускается при старте API и каждые пять минут.
   Коды проектов сопоставляются с локальной проекцией LK; сначала выполните
   штатный `lk:sync`, если она ещё не заполнена.

Каталог обновляется идемпотентно по ERP UID / canonical chat UUID; физического
удаления нет. Помеченные на удаление кандидаты исключаются из каталога,
отправка им запрещена. Конфликт идентичностей сохраняет существующие данные и
выводит диагностическое предупреждение. Redis lock ограничивает один запуск;
запуск ограничен четырьмя минутами и 1000 страницами. Продолжение большого
каталога хранится после полностью применённой страницы; прерванная страница
применяется повторно. Отсутствие Redis/ERP сохраняет предыдущий каталог.

## Доставка и обновления

Отправка резервирует операцию и вложение вместе с аудитом в короткой
транзакции MariaDB. Сетевой вызов выполняется вне транзакции; результат и аудит
фиксируются вместе. Повтор с тем же ключом и содержимым возвращает прежнюю
операцию, с другим содержимым — 409. ERP дополнительно резервирует запрос в
собственном регистре до обращения к провайдеру.

При потере подтверждения результат — `UNKNOWN`, автоматической повторной
отправки нет. Оператор должен проверить историю перед новым сообщением.
Старая `PENDING` операция после двух минут также отображается как `UNKNOWN`.
Перезапуск API не вызывает повторной отправки.

SSE использует короткоживущий opaque grant в заголовке Authorization, без
токена в URL. Срок ограничен пятью минутами и сроком JWT. Сервер перепроверяет
доступ к объекту каждые пять секунд. LK уведомляет сразу; для ERP уведомление
каждые пять секунд инициирует чтение истории. При обрыве/зависании SSE клиент
переподключается с задержкой, а REST polling продолжает обновления.

Вложения истории имеют подписанный locator, привязанный к кандидату, а для
ЛК — и к текущему chat UUID. Перед скачиванием EDO повторно проверяет доступ.
Разрешены только пути `/upload/` и `/uploads/` заданного nginx ЛК, без
редиректов. Файл копируется в закрытый S3 и выдаётся по URL на 60 секунд.
Подготовленный к отправке файл действует 24 часа. Для временных копий
`communications/` настройте lifecycle bucket на удаление через два дня;
исходники доставленных сообщений остаются в ЛК/ERP. Lifecycle не должен
затрагивать остальные префиксы документов EDO. Метаданные операций и аудит
не удаляются этим правилом.

## Проверка и откат

Локально: `pnpm local:up`, затем `https://edo.localhost:12443/review`.
Без опубликованного ERP endpoint и настройки chat-server новый интерфейс
доступен, но полноценная межсистемная переписка недоступна. Временный UI preview
на другом порту с фиктивными данными не подтверждает интеграцию.

Для приёмки на тестовой базе 1С проверить реальные отправку/ответ/файл во всех
четырёх каналах, запись фактического автора, одновременные окна 1С и EDO,
ограничение по объекту, повтор запроса и потерю подтверждения. BSL Language
Server и тесты адаптера не заменяют проверку на платформе 1С.

Изменения находятся в отдельных ветках EDO, ERP и ЛК; их можно выпускать и
откатывать отдельно. Для отключения нового импорта установить
`CANDIDATE_CATALOG_SYNC_ENABLED=false`. При откате приложения оставить
добавленные таблицы/колонки и регистр идемпотентности: старый код их не
использует, а сохранённые операции защищают от повторной отправки. Не удалять
данные/volumes и не восстанавливать всю базу ради отката интерфейса.

При будущем production deployment учесть известный блокер внешнего
`ci-templates/edo.yml`: генерация `.env` теряет `ERP_CANDIDATE_URL/TOKEN`.
Новые communications settings также должны попасть в шаблон до включения.
После deploy проверить наличие настроек в `.env` и API container без вывода
значений. Сам этот change не выполняет deployment.
