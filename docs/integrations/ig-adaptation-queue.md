# Очередь ИГ по допуску к адаптации

1С передаёт `operationId` вместе с каждым сотрудником в запросе допуска к «7 шагам». Сервис surveys обычно сохраняет допуск и событие для ЭДО в одной транзакции. Если новая запись события не удалась, сервис повторяет сохранение допуска без события, чтобы не блокировать действующие «7 шагов», и пишет ошибку в журнал. В этом случае доставка в ЭДО не гарантирована: после устранения ошибки нужно повторить отправку. ЭДО подтверждает сохранённое событие только после создания карточки и загрузки прежних документов. Повтор одной операции безопасен.

В surveys необходимо применить миграцию `20261103100000_edo_adaptation_grant_events` и задать отдельный секрет `EDO_ADAPTATION_SYNC_TOKEN`. В ЭДО применить миграцию `20261103150000_ig_employment_cycles` и настроить `EDO_ADAPTATION_SYNC_ENABLED=true`, `EDO_ADAPTATION_EVENTS_URL` на `.../surveys-service/api/internal/edo/adaptation-grant-events` и тот же `EDO_ADAPTATION_SYNC_TOKEN`. В production адрес должен использовать HTTPS. Без этих настроек синхронизация отключена.

По прямому указанию пользователя тестовая 1С отправляет запросы на рабочий `https://lk.sps38.pro/surveys-service/api/adaptation/access-grants`. Это изменяет реальные допуски выбранных сотрудников в рабочем ЛК; для проверки пользователь сам выбирает людей в 1С. Ошибка HTTP-запроса показывается в форме и не прерывает дальнейшую работу с ней.

Существующие допуски не импортируются автоматически. Для проверки нужны новые отправки на «7 шагов»; тестовые физлица и данные в 1С создаёт пользователь. До обновления и настройки всех трёх компонентов сквозной сценарий недоступен. События хранятся в surveys до подтверждения ЭДО; ошибки интеграции видны в журнале API ЭДО без содержимого запросов и секретов.

### Проекция заездов ИГ

Синхронизация заездов включается отдельно: `EDO_ARRIVAL_SYNC_ENABLED=true`, `ERP_COMMUNICATIONS_URL` указывает на согласованный ERP candidate-communications endpoint, `EDO_ARRIVAL_CONTEXTS_URL` — на `https://<host>/surveys-service/api/internal/edo/arrival-contexts`, а `EDO_ADAPTATION_SYNC_TOKEN` должен совпадать с токеном Surveys. В production разрешён только HTTPS. По умолчанию процесс выключен; он не устанавливает cron и не создаёт очередь.

Проекция сохраняет подтверждённую ревизию каждого человека и историю идентификаторов участия. Отсутствие человека в неполном проходе не отменяет запись. Неподтверждённая отправка в Surveys остаётся в `ig_arrival_persons.syncPending` для повторной доставки той же ревизии; техническая причина находится в `syncError`, конфликт привязки — в `bindingError`. Ошибки отдельных записей источника сохраняются в `ig_arrival_issues` с хешем идентификатора и безопасным кодом, а не с исходными данными человека; аудит сохраняется атомарно. Не исправляйте конфликт изменением идентификатора участия или повторным назначением владельца вручную.

Список заездов использует календарную дату ERP и UUID объекта без преобразования часового пояса. Отменённое текущее участие исключается из очереди, исторические участия сохраняются. При недоступности ERP ранее проверенная привязка к карточке сохраняется, а отправка в Surveys откладывается до повторной проверки. Обновление профиля ERP и автоматический импорт предыдущих документов для карточек, впервые увиденных через заезд, требуют следующего отдельного этапа; сама проекция не доказывает прохождение этапов оформления.

Счётчики очереди считают людей, а не документы. Основное состояние выбирается по приоритету: подтверждённое оформление → возвращённый документ → проверка/обработка → отправка или ожидание передачи в ERP → ожидание документов. Признак `needsAttention` независим от этого состояния. Название объекта не входит в ключ группы.

Очередь ИГ и доставка в Surveys включают только записи с сохранённым признаком `igVerified`: он устанавливается после точного подтверждения ERP физлица, кода и направления ИГ. Миграция оставляет прежние записи неподтверждёнными до следующей проверки. При временной сетевой недоступности ранее подтверждённая привязка сохраняется; явный конфликт или нарушение контракта ERP снимает подтверждение. Неизменённая ревизия без ошибки привязки использует сохранённое подтверждение, поэтому источник обязан повышать ревизию при изменении идентичности или направления; проверка документа перед отправкой в ERP выполняется отдельно.
