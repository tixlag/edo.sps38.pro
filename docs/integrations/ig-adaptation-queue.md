# Очередь ИГ по допуску к адаптации

1С передаёт `operationId` вместе с каждым сотрудником в запросе допуска к «7 шагам». Сервис surveys обычно сохраняет допуск и событие для ЭДО в одной транзакции. Если новая запись события не удалась, сервис повторяет сохранение допуска без события, чтобы не блокировать действующие «7 шагов», и пишет ошибку в журнал. В этом случае доставка в ЭДО не гарантирована: после устранения ошибки нужно повторить отправку. ЭДО подтверждает сохранённое событие только после создания карточки и загрузки прежних документов. Повтор одной операции безопасен.

В surveys необходимо применить миграцию `20261103100000_edo_adaptation_grant_events` и задать отдельный секрет `EDO_ADAPTATION_SYNC_TOKEN`. В ЭДО применить миграцию `20261103150000_ig_employment_cycles` и настроить `EDO_ADAPTATION_SYNC_ENABLED=true`, `EDO_ADAPTATION_EVENTS_URL` на `.../surveys-service/api/internal/edo/adaptation-grant-events` и тот же `EDO_ADAPTATION_SYNC_TOKEN`. В production адрес должен использовать HTTPS. Без этих настроек синхронизация отключена.

По прямому указанию пользователя тестовая 1С отправляет запросы на рабочий `https://lk.sps38.pro/surveys-service/api/adaptation/access-grants`. Это изменяет реальные допуски выбранных сотрудников в рабочем ЛК; для проверки пользователь сам выбирает людей в 1С. Ошибка HTTP-запроса показывается в форме и не прерывает дальнейшую работу с ней.

Существующие допуски не импортируются автоматически. Для проверки нужны новые отправки на «7 шагов»; тестовые физлица и данные в 1С создаёт пользователь. До обновления и настройки всех трёх компонентов сквозной сценарий недоступен. События хранятся в surveys до подтверждения ЭДО; ошибки интеграции видны в журнале API ЭДО без содержимого запросов и секретов.
