# Локальный стенд EDO

## Открыть и войти

Адрес: **https://edo.localhost:12443**. Nginx общий с ЛК;
https://next.localhost:12443 продолжает обслуживать ЛК.

Используется **ваша учётная запись ЛК**; демо-вход отключён.

1. Войти в ЛК: https://next.localhost:12443/public/auth обычными логином и паролем.
2. В том же браузере открыть https://edo.localhost:12443.
3. EDO восстановит сессию через auth-service ЛК. После выхода из ЛК перезагрузить
   EDO; новая сессия больше не восстановится.

Access JWT хранится только в памяти страницы, refresh — в HttpOnly cookie ЛК.
EDO проверяет подпись HS256, issuer, срок и права на backend. `JWT_SECRET` в
корневом `.env` согласован с работающим локальным `lk_auth-service` (значение в
Git не записывается). Логин/пароль EDO не создаются, пароли в EDO не передаются.

Минимум для просмотра: право 20000 и область объектов (20009/20008 — все,
20007 — конкретные объекты). При отсутствии прав администратор назначает их в ЛК;
скрипт запуска сам их не выдаёт.

```dotenv
NODE_ENV=development
API_PORT=3001
CORS_ORIGIN=https://edo.localhost:12443
VITE_API_BASE_URL=https://edo.localhost:12443
VITE_AUTH_REFRESH_URL=https://next.localhost:12443/api/auth/v1/refresh-tokens
ALLOW_INSECURE_DEV_AUTH=false
VITE_ALLOW_INSECURE_DEV_AUTH=false
OCR_MODE=disabled
S3_ENDPOINT=http://127.0.0.1:5000
```

Скрипт добавляет точное разрешение CORS для `https://edo.localhost:12443` только
на маршруте refresh в локальном nginx ЛК; другие origins и маршруты сохраняют
прежнее поведение. У ЛК и EDO разные локальные домены, поэтому браузер должен
разрешать отправку cookie ЛК при запросе из EDO. Если показано «Требуется вход через
LK»: проверить вход в том же браузере, разрешение сторонних cookie для этих двух
локальных сайтов и доверие сертификату ЛК. При 403 на пользовательском API —
проверить права EDO. При 401 — действующую сессию и совпадение JWT-настроек.

В production флаги демо-входа также остаются `false`; адрес refresh указывает на
боевой auth-service ЛК. Локальная nginx-вставка не является конфигом production.

## Что посмотреть

- Шапка и меню: ваш профиль из ЛК, область доступа и текущая дата. ФИО и должность
  берутся из локальной проекции ЛК по проверенным `code_1c`/UUID сессии. Если записи
  нет или UUID неоднозначен, показывается идентификатор учётной записи и сообщение
  об отсутствии профиля; вымышленное имя не подставляется.
- Дашборд: сводка и этапы по БД EDO с проверкой области доступа; задачи и история
  действий — только текущей учётной записи. Фиксированных демо-счётчиков нет.
- `/employees`: дела оформления EDO в вашей области доступа и переход в карточку.
  Базовый seed создаёт пять тестовых дел; `pnpm local:example` добавляет шестое —
  пример паспорта. Они не являются вашим профилем и видны только при подходящих
  правах. Справочник сотрудников ЛК не создаёт дела автоматически.
- Карточка работника: текущий реализованный экран, навигация назад/вперёд.
- В карточке работника есть просмотр документов: оригиналы, поля OCR, замечания,
  исходный JSON, ручные исправления и подтверждение при наличии права 20002/20009.
  Раздел «Проверка документов» в меню пока не содержит общей очереди.
- Остальные разделы меню пока содержат заглушки.
- Swagger: https://edo.localhost:12443/api/docs. Для пользовательских API в
  `Authorize` → `access-jwt` указать действующий JWT учётной записи без `Bearer`.
  Серверные ручки чатов требуют отдельного `EDO_LK_INTERNAL_TOKEN`.

OCR отключён до получения URL и контракта. Для загрузки в этом режиме API вернёт
`OCR_NOT_CONFIGURED` после успешной серверной авторизации. Синтетическое
распознавание автоматически не включается.

### Пример загруженного паспорта

Открыть [карточку Иванова Ивана Ивановича](https://edo.localhost:12443/employees/emp-passport-example).
Это отдельное тестовое дело, не профиль вошедшего пользователя. Внизу карточки:

1. «Документы» → «Паспорт»: два вымышленных изображения, хранящихся в локальном S3.
2. «OCR завершено», «Проверка»: распознавание успешно, ручное подтверждение ещё требуется.
3. «Распознанные поля»: ФИО, серия/номер, даты, выдача, регистрация.
4. «Исходный JSON OCR»: раскрыть для просмотра ответа до исправлений.
5. Обновлённый пример содержит 10 областей и намеренную ошибку OCR: номер `00000O`
   вместо `000000`. Нажать на бокс номера → значение в редакторе получит фокус и
   выделится → исправить → «Сохранить исправления». Редакторы сразу доступны
   с правом 20002/20009 в статусе «Проверка» и растут по высоте для длинных значений.
6. «На превью» возле поля выбирает нужный файл/страницу и прокручивает к превью;
   на узком экране оригинал и поля идут друг под другом, на широком — рядом.
   Можно увеличить картинку и скрыть/показать области. «Подтвердить документ»
   доступно после сохранения правок.
   Изменения пишутся в БД с аудитом; исходный JSON, текст и боксы OCR сохраняются.

Результат явно помечен `STUB` и «Тестовый пример». Внешний OCR не вызывался,
`OCR_MODE=disabled` сохраняется. Формат примера описывает внутренний адаптер EDO,
не будущий контракт сервиса OCR. Для PDF работает превью страниц с теми же боксами;
оригинал можно скачать. Локальный S3 разрешает чтение PDF из EDO через CORS.

После пересоздания локального S3 пример можно восстановить:

```sh
pnpm local:example
# На новой БД можно явно выбрать объект, доступный вашей учётной записи:
pnpm local:example -- --location-id=98
```

По умолчанию объект примера — 98; область доступа проверяется обычным API.
При изменении набора примера создаётся следующая версия, предыдущие остаются в истории.
Повторный запуск сохраняет ручные исправления и подтверждение текущей версии, восстанавливая
только те же оригиналы. Скрипт разрешён только в development с локальными S3
и MariaDB `edo`; реальные дела и справочник ЛК он не меняет.

## Запустить повторно

Нужны Linux, уже запущенный обычный стек ЛК, заполненный корневой `.env`, `pnpm`, Docker
и `mkcert` с доверенным локальным CA. На новой машине сначала:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm db:migrate
# Только для создания/обновления демонстрационных данных в локальной БД edo:
pnpm db:seed
```

Затем:

```sh
pnpm local:up
pnpm local:status
# Остановить только процессы API/Web EDO:
pnpm local:down
```

`local:up` запускает API и Vite в фоне (терминал можно закрыть), проверяет занятые
порты, использует текущий `lk_nginx`, создаёт сертификат EDO через существующий CA,
проверяет конфигурацию nginx перед reload и запускает только EDO S3.
Повторный вызов не создаёт дополнительные процессы. Процессы не настроены на
автозапуск после перезагрузки ОС — после неё снова вызвать `pnpm local:up`.

Файлы виртуального хоста и сертификата устанавливаются в работающий контейнер
`lk_nginx`; после его **перезапуска или пересоздания** снова вызвать `pnpm local:up`.
Исходники находятся в `ops/local/edo.nginx.conf.template` и
`ops/local/lk-refresh-cors.nginx.fragment`. В работающий виртуальный хост ЛК
добавляется только точный маршрут refresh с CORS; исходные файлы репозитория ЛК
не меняются. При неудачном `nginx -t` конфиги восстанавливаются. Общие контейнеры,
очереди и Docker volumes не удаляются.

API слушает `3001`, Web — `5174` (порт `5173` остаётся ЛК). Снаружи браузер использует
один HTTPS origin, включая `/api/*`; nginx проксирует HMR WebSocket.
API и локальный Vite принимают заголовки до 128 KiB, поскольку JWT ЛК с правами
доступа может превышать стандартный лимит Node.js.
Если домен не разрешается в loopback, добавить `127.0.0.1 edo.localhost` в `/etc/hosts`.
При предупреждении сертификата проверить доверие к CA через `mkcert -install`.

Логи и служебные файлы: `.cache/local-stand/`; ключ сертификата не коммитится.
После смены `.env` перезапустить: `pnpm local:down` → `pnpm local:up`.

Проверка готовности: https://edo.localhost:12443/api/health/ready.
Интеграция: https://edo.localhost:12443/api/health/integration.
Компактный HTTP API ЛК отдельно требует парного токена
`EDO_INTERNAL_TOKEN` у ЛК / `LK_EDO_INTERNAL_TOKEN` у EDO. Сейчас локальный ЛК
возвращает 500 для этой интеграции; уже сохранённая проекция и RabbitMQ consumer
работают. `local:up` не меняет настройки auth-service/PHP ЛК и не запускает snapshot.

## S3 локально и в production

Локально используется уже существующий `edo-s3` (moto) на `:5000`, бакет
`edo-documents` создаётся при `local:up`, если отсутствует. Moto — эмулятор для
разработки; его данные не следует считать долговечными после пересоздания
контейнера, а настройки приватности не заменяют проверку на настоящем S3.
Для локального MinIO есть отдельный профиль в `docker-compose.yml` (его порты
9000/9001 могут быть заняты PHP ЛК — перед запуском выбрать свободные).

В production EDO подключается к **существующему S3, который использует ЛК**:
отдельное хранилище поднимать не требуется. Настроить в корневом `.env`:

```dotenv
S3_ENDPOINT=https://<тот-же-endpoint-что-у-ЛК>
S3_REGION=<регион-хранилища>
S3_BUCKET=edo-documents
S3_ACCESS_KEY=<отдельный-ключ-EDO>
S3_SECRET_KEY=<секрет-ключа-EDO>
```

Сервер S3 общий; рекомендуется отдельный закрытый бакет `edo-documents` и доступ
EDO только к нему. Если оператор выберет общий бакет, ключи EDO находятся под
`documents/<documentId>/v<version>/...`; нужно проверить отсутствие пересечения
с префиксами ЛК и ограничить доступ EDO этим префиксом. Внешние бакеты скрипт
`local:up` не создаёт и не меняет. Подписанные ссылки доступны браузеру/OCR пять
минут: endpoint должен быть достижим ими, включая будущий OCR в локальной сети.

Оригиналы хранятся в S3, JSON OCR — в MariaDB. Подробный контракт:
[документы кандидата](../integrations/edo-candidate-documents.md).
