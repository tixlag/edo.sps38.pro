# Договоры из ЗУП: реализованный этап

Реальные PDF, получатели, версии, S3 и уведомления. **Подписание демонстрационное:** Sign.Me, банки и проверка УКЭП не подключены. Записи `mode=demo` не являются электронной подписью.

## Сценарий

1. В `/review-ig` кадровик нажимает «Договор» кандидата. Сервер получает типы из ЗУП, берёт ФИО и дату рождения из карточки, запрашивает PDF и сохраняет черновик.
2. Кадровик проверяет PDF и может заменить его своим PDF/DOCX. При недоступности ЗУП можно создать черновик для ручной загрузки. DOCX преобразуется в PDF; исходный DOCX также сохраняется.
3. Кадровик первым проходит имитацию Sign.Me/УКЭП. Одним действием сервер фиксирует его демоподтверждение и отправку неизменяемой версии.
4. Сотрудник открывает `/my-documents` с сессией ЛК и проходит демонстрационный выбор банка с отдельным подтверждением либо отказывается от подписи.
5. После подтверждения сотрудника отправителю приходит уведомление в ЭДО. В S3 остаются неизменный PDF, исходный DOCX при наличии и `confirmations-demo.json` с обеими записями, хешем версии и временем. Штампы и страницы в PDF не добавляются.

Без `code1c` подготовка разрешена, отправка запрещена. Код получателя фиксируется при отправке: изменение связи в карточке не передаёт договор другому сотруднику. Замена файла разрешена только до отправки; исправленный отправленный договор оформляют новым процессом.

## Настройки

Корневой `.env`, только серверные переменные:

```dotenv
ZUP_DOCUMENTS_BASE_URL=http://10.10.2.0/ZUP3_SPS_labs/hs/zup-documents/
ZUP_DOCUMENTS_BASIC_AUTH=
ZUP_DOCUMENTS_API_KEY=
CONTRACT_LIBREOFFICE_BIN=libreoffice
```

`ZUP_DOCUMENTS_BASIC_AUTH` — Base64-значение после `Basic `, без префикса. API key отправляется в `X-API-Key`. Не использовать `VITE_*` для секретов. При пустых настройках доступна ручная подготовка.

Локально для DOCX нужен LibreOffice Writer и шрифты с кириллицей. Production API image включает Writer, Liberation и DejaVu. При отсутствии конвертера загрузите PDF. Ограничения: файл 50 МБ, PDF 100 страниц, конвертация 60 секунд, два одновременных процесса. Временные файлы и отдельные профили находятся в `.cache/contracts/` и удаляются после обработки. DOCX с внешними связями, макросами и встроенными объектами отклоняются; используйте готовый PDF.

Сессия восстанавливается существующим `VITE_AUTH_REFRESH_URL` через HttpOnly cookie. Локальный адрес: `https://next.localhost:12443/api/auth/v1/refresh-tokens`. Нужны действующая сессия ЛК и CORS для origin ЭДО. JWT остаётся в памяти. Кнопка в самом ЛК не входит в этап.

## Права и API

Кадровые действия требуют `20003 — EDO_SIGNING` либо `20009`. Получатели ограничены разрешёнными объектами, всеми объектами по 20008/20009 или разрешённой группой проверки без географического ограничения. Проверка/аудит без 20003 не дают кадровых действий. Пока 20003 разрешает все типы договоров; ограничения по сертификатам вводятся с настоящим оператором.

Собственные договоры доступны без административных прав: сервер проверяет `code_1c` подтверждённого JWT. Гостевого доступа через чат нет.

Административные маршруты: `/api/contracts`, `/api/contracts/types`, `/api/contracts/candidates/:candidateId`, `/api/contracts/:id`, `/api/contracts/:id/file`, `/api/contracts/:id/send`, `/api/contracts/notifications`, `/api/contracts/notifications/:id/read`.

Собственные: `/api/my/contracts`, `/api/my/contracts/:id`, `/api/my/contracts/:id/confirm`, `/api/my/contracts/:id/decline`. DTO и operationId опубликованы в OpenAPI; UI использует сгенерированный `@edo/api-client`.

Изменения принимают UUID `requestId` и, кроме создания, ожидаемую `revision`. Повтор сетевого запроса сохраняет requestId; новый процесс/файл/действие получает новый. Списки ограничены 100 последними договорами/уведомлениями. Открытые страницы обновляются каждые 10 секунд и при фокусе. Ссылки S3 действуют 5 минут; кнопка обновления просмотра получает свежую ссылку, не сбрасывая чтение при каждом опросе.

Состояния: `PREPARING → DRAFT → WAITING_EMPLOYEE → COMPLETED | DECLINED`; ошибка формирования — `FAILED` с ручной загрузкой. Прерванная подготовка становится `FAILED` после 10 минут. Ошибка сохранения журнала не завершает договор. Незакреплённые объекты S3 убираются через час; атомарный захват очисткой запрещает позднее закрепление. Изменения состояния, подтверждения, уведомления и аудит транзакционны.

## Проверка и выпуск

Миграции: `0023_signing_contracts`, `0024_contract_object_cleanup_claim`; применять через `pnpm db:migrate` к базе `edo`. Production-деплой не входит в этап.

```sh
pnpm --filter @edo/api exec vitest run test/signing-contracts.spec.ts test/zup-documents.client.spec.ts test/contract-file.spec.ts
pnpm --filter @edo/web test
```

Для lifecycle-тестов установить `EDO_CONTRACT_TEST_DATABASE_URL` только на одноразовую локальную MariaDB, базу `edo` на нестандартном порту, после применения миграций. Тесты очищают таблицы; не направлять их в общую или production-базу. Без переменной проверки MariaDB пропускаются, проверки политики доступа выполняются.

Настоящий Sign.Me, проверка УКЭП, полномочия по типам, обратная передача в ЗУП и гостевой путь — отдельные этапы.
