# Спецификация: Поэтапная загрузка документов кандидата в Личном Кабинете (LK) и EDO

**Дата:** 2026-11-07  
**Статус:** Согласовано  
**Область:** `lk.sps38.pro` (`public_next`), `edo.sps38.pro` (`apps/api`, `packages/api-client`)

---

## 1. Контекст и цели

### Проблема
В Личном Кабинете (со страницы адаптации и в чате с кандидатом) загрузка документов отображалась сплошным неструктурированным рядом («кругляшки» от 1 до N). Кандидату или новому сотруднику было трудно ориентироваться:
- Не понятно, какие документы нужны прямо сейчас (например, до заезда на объект), а какие относятся к оформлению и заезду.
- В чате кандидата находился громоздкий развернутый список форм с дублирующимися кнопками и инпутами.
- Отсутствовала наглядная группировка по этапам, аналогичная разделению на этапы в кабинете проверки документов EDO (`ReviewPage` и `CandidateDrawer`).

### Цели
1. Разбить загрузку документов на этапы («Этап 1», «Этап 2», «Этап 3»...) строго по правилам 1С/EDO, без вымышленных названий.
2. Отобразить этапы кружками с двухкольцевой диаграммой статусов (как в EDO `StageRing`):
   - **Внутренний круг:** Обязательные документы этапа (`required`).
   - **Внешний круг:** Дополнительные документы этапа (`additional`).
   - **Цвета сегментов:** Соответствуют актуальным статусам документов (`#22c55e` одобрен/зачтен, `#f97316` на проверке, `#ef4444` возвращен, `#cbd5e1` не загружен).
   - В центре кружка — номер этапа (`1`, `2`, `3`).
3. Сохранить инпуты для расшифровки полей документа (серия, номер, дата выдачи и т.д.) со стимулирующей плашкой:
   *«⚡ Заполните данные документа, чтобы проверка прошла быстрее:»*.
   Слово «необязательно» убрать из интерфейса, но технически отправку не блокировать, если поля остались пустыми (OCR распознает данные автоматически, а верификатор EDO проверит).
4. Обеспечить последовательную съемку многостраничных документов через нативную камеру (`capture="environment"`):
   - Разворот паспорта (стр. 1) → кнопка «📷 Снять еще фото» → регистрация/прописка (стр. 2) → превью с возможностью удаления и сортировки.
5. Обеспечить сквозной зачет документов: если документ привязан к нескольким этапам (например, паспорт в Этапе 1 и Этапе 2), он загружается один раз и на последующих этапах автоматически отображается как принятый.
6. Унифицировать чат кандидата и адаптацию: в чате кандидата заменить длинную простыню форм на компактный виджет с кружками этапов, открывающий единую модалку загрузки.

## 2. Архитектура и контракты данных

### 2.1. Расширение контракта каталога документов (EDO API)
В `CatalogDocumentTypeDto` помимо существующего массива этапов `stages: (number | null)[]` добавляется детализация категорий по каждому этапу:

```typescript
export interface CatalogDocumentStageCategoryDto {
  stage: number | null;
  category: "required" | "additional";
}

export interface CatalogDocumentTypeDto {
  code: string;
  title: string;
  documentUid: string;
  stages: (number | null)[];
  stageDetails?: CatalogDocumentStageCategoryDto[];
  fields: DocumentDefinitionDto[];
}
```

В `DocumentCatalogService.list`:
Функция `classifyRule(rule, position, citizenship, project)` уже вычисляет категорию `"required" | "additional"`. Эти данные собираются в `stageDetails`:
```typescript
stageDetails: (t.stageRules?.length ? t.stageRules : [t])
  .filter((rule) => classifyRule(rule, position, citizenship, project) !== null)
  .map((rule) => ({
    stage: rule.stage ?? null,
    category: classifyRule(rule, position, citizenship, project)!,
  }))
```

## 3. Пользовательский интерфейс и компоненты (LK Frontend)

### 3.1. Компонент двухкольцевой диаграммы этапа (`StageDonutRing`)
Переиспользуемый компонент SVG-диаграммы (адаптированный из `apps/web/src/pages/ReviewPage.tsx` под стиль LK):
- **Внутреннее кольцо (r=19, strokeWidth=3.5):** Обязательные документы этапа.
- **Внешнее кольцо (r=25, strokeWidth=3):** Дополнительные документы этапа.
- Длина дуг вычисляется пропорционально количеству документов в соответствующих статусах:
  - `approved` / `reused` / `signed` → зеленый (`#22c55e`)
  - `inReview` / `pending` → оранжевый (`#f97316`)
  - `processing` / `ocrPending` → синий/фиолетовый (`#3b82f6`)
  - `returned` → красный (`#ef4444`)
  - `missing` → серый полупрозрачный (`#94a3b8`)
- В центре — номер этапа (`1`, `2`, `3`). При активности этап подсвечивается мягким белым свечением (`ring-active-glow`).
- Легенда в модалке не отображается для максимальной лаконичности интерфейса.

### 3.2. Модалка загрузки (`DocumentsModal`)
- **Шапка:**
  - Заголовок: «Загрузка документов».
  - Ряд кружков этапов (`StageDonutRing`): «Этап 1», «Этап 2», «Этап 3» со счетчиками (`1/3 готово`).
  - По умолчанию открывается первый незавершенный этап.
- **Под шапкой:**
  - Горизонтальная полоса чипсов документов выбранного этапа (например, `[✓ Паспорт РФ] [● СНИЛС] [Водительское]`).
- **Тело выбранного документа (`DocumentPanel`):**
  - Превью загруженных страниц (миниатюры с номерами 1, 2..., кнопкой удаления ✕ и кнопками перемещения).
  - Кнопки источников:
    - «📷 Снять фото» (при наличии страниц — «📷 Снять еще фото») с атрибутом `capture="environment"` для мгновенного вызова мобильной камеры.
    - «📁 Загрузить файл» (выбор из галереи или PDF).
  - Мотивационный блок для ускорения проверки:
    - Плашка: *«⚡ Заполните данные документа, чтобы проверка прошла быстрее:»* (без слова «необязательно»).
    - Поля ввода (серия, номер, дата выдачи, кем выдан и т.д.), настроенные для данного типа документа.
    - При отправке: пустые поля игнорируются, отправка не блокируется.
  - Кнопка действия:
    - «Отправить [Название документа] на проверку →».
    - Ссылка «Загрузить позже».

### 3.3. Виджет документов в чате с кандидатом (`CandidateChatDocumentsWidget`)
- Заменяет старый длинный раскрывающийся блок `<details>` с сырыми формами на аккуратный мобильный виджет:
  - Кружки этапов со статусами-диаграммами.
  - Компактный список документов текущего этапа.
  - Кнопка «Загрузить документы Этапа N», открывающая модалку `DocumentsModal` на нужном документе.

### 3.4. Список документов на странице адаптации (`DocumentsList`)
- Документы на странице шага адаптации разделяются на секции с заголовками «Этап 1», «Этап 2», «Этап 3» вместо одного длинного списка.

## 4. План тестирования и валидации

1. **Unit-тесты логики этапов:**
   - Корректная группировка документов по этапам из `CatalogDocumentTypeDto`.
   - Корректный подсчет секторов диаграммы (обязательные/дополнительные и их статусы).
   - Сквозной зачет документов между несколькими этапами.
2. **UI-проверка на мобильных устройствах и десктопе:**
   - Последовательное добавление 2+ фото через камеру (многостраничный паспорт).
   - Отправка формы с заполненными полями и с пустыми полями (без блокировок).
   - Переключение этапов по клику на кружки диаграммы.
   - Проверка работы в адаптации и в чате кандидата.
