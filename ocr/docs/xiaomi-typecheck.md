# Xiaomi OCR для проверки типа документа

Проверка типа использует отдельный процесс `services/typecheck/server.py`, Python 3.12 и закреплённую модель [Xiaomi-OCR-0](https://huggingface.co/xiaomi-research/Xiaomi-OCR-0) (Apache 2.0). Ревизия и SHA-256 каждого файла находятся в `models/xiaomi-manifest.json`; загрузка выполняется до переключения служб. RU/UZ сохраняют свои окружения, Paddle и GLM для распознавания полей. Модель Xiaomi не получает ожидаемый тип, список типов или вопрос о соответствии: единственный запрос — `Extract the text in the image.`

Полная страница уменьшается до 786432 пикселей без обрезки. Ограничения: один запрос одновременно, 10 МиБ входа, 40 млн исходных пикселей, 8192 входных токена, 2048 выходных токенов, до 45 секунд на страницу в общем бюджете endpoint 55 секунд. CUDA использует BF16 и лимит allocator 23% VRAM; CUDA context и другие процессы не входят в этот лимит. Проверять общий расход через `nvidia-smi` обязательно. Генерация без EOS, превышение лимита или срока даёт техническую неопределённость, частичный текст не классифицируется.

Правила `document-type-rules-v2.json` дополняют исходный реестр. Для решения нужны отличительный заголовок и независимый подтверждающий признак либо два независимых заголовка. Перекрывающиеся фразы считаются одним признаком. В исходном режиме остаются прежние формулировки. В журнал попадают только коды решений, причины и длительность; текст и изображения остаются в частных материалах проверки.

## Контракт v3

`POST :8000/document-check` с `expected_code` возвращает `policy_version=document-check-v3` только при `DOCUMENT_TYPE_PROVIDER=xiaomi`. Без `expected_code` сохраняется проверка наличия документа v1. Ответ содержит прежние оценки наличия документа и отдельные `type_model`, `type_model_revision`, `type_rules_version`, `type_reason`, `type_pages[].{verdict,detected_code,source,reason,matched_phrases,elapsed_ms}`. Источник типа — `XIAOMI_RULES`.

`MISMATCH` допустим только если **каждая** страница уверенно определена как один и тот же другой тип. Нечитаемая страница, техническая ошибка или разные чужие типы исключают автоматический возврат. Ожидаемый и чужой документ в одном пакете дают `UNCERTAIN/MIXED_DOCUMENT_TYPES`. `MATCH` подтверждает только тип: новый документ остаётся `IN_REVIEW`, оператор проверяет изображение и реквизиты. Существующий предел двух возвратов сохраняется; третья загрузка поступает оператору.

API проверяет закреплённую модель, версию правил, полное покрытие страниц, согласованность итогов и минимум два независимых доказательства. v1/v2 сохраняют совместимость. Недоступность OCR, неверный JSON, неподтверждённая ревизия, обрезанный текст и таймаут не расходуют попытки автоматического возврата. Сообщение при уверенном несовпадении: «Загружен документ „СНИЛС“ вместо ожидаемого „НАКС“».

## Порядок выпуска

1. Выпустить код OCR через MR и защищённую `main`. По умолчанию `DOCUMENT_TYPE_PROVIDER=legacy`; новая модель не запускается и не меняет решения.
2. Администратору один раз установить дополнительный unit из проверенного релиза: `sudo python3 /home/neuro/.local/share/edo-ocr/current/deploy/runner/install_typecheck.py --user neuro`. Установщик делает резервную копию unit/control wrapper, обновляет разрешённую команду управления и выполняет daemon-reload/enable. Действующие API и runner не перезапускаются. Прежних sudo-прав CI хватает для последующих выпусков, но не для этой первоначальной установки.
3. Задать `DOCUMENT_TYPE_PROVIDER=shadow` в `shared/config/uz.env`, затем выпустить новый OCR commit через runner. Для нового окружения требуется минимум 10 ГиБ свободного диска до установки; installer не удаляет старые окружения, веса или чужие кэши. Подготавливаются отдельное окружение, проверенные веса и systemd-служба на `127.0.0.1:8084`. `shared/config/typecheck.env` может задавать `XIAOMI_GPU_MEMORY_FRACTION` (0..0.35, стандарт 0.23). UZ обращается через `DOCUMENT_TYPE_XIAOMI_URL=http://127.0.0.1:8084/recognize-text`. Порты 8000/8001/8083 сохраняются.
4. Проверить shadow на частных документах и подготовить независимый набор ниже. После подтверждения пользователем успешного OCR runner отдельно выпустить API/web с поддержкой v3. `OCR_MODE` и worker не включаются этим изменением.
5. После проходящего gate задать `DOCUMENT_TYPE_PROVIDER=xiaomi` и выпустить следующий OCR commit. Прямое изменение provider у уже подготовленного SHA отклоняется: создайте новый commit через MR, чтобы переключение проверял runner. При проблемах вернуться к `legacy` с новым выпуском. Не редактировать `current` вручную.

Health нового процесса проверяет загрузку закреплённой модели. После запуска runner выполняет реальные запросы для прежних RU/UZ/миграционного распознавания. Ошибка вызывает обычный откат current/служб/GLM. На откате к версии без окружения Xiaomi unit пропускается по `ConditionPathExists`.

## Независимая проверка качества

Материалы хранятся вне Git. Пример структуры corpus manifest:

```json
{"samples":[{"id":"snils-01","code":"SNILS","path":"samples/snils-01.jpg","source_url":"https://example.org/public-example.jpg","split":"heldout"}]}
```

Для каждого из 29 типов требуются минимум три независимых публичных источника с разными изображениями, два из них — `heldout`. Источники heldout не должны использоваться для настройки правил. Повороты/размытие/кропы одной картинки не считаются независимыми документами. Разметку и независимость источников проверяет человек.

На OCR-сервере, из проверенного компонента:

```bash
services/uz/.venv/bin/python scripts/evaluate_typecheck.py \
  --manifest /private/typecheck/corpus.json \
  --output /home/neuro/.local/share/edo-ocr/shared/var/verification/typecheck
```

Скрипт читает каждое изображение Xiaomi один раз, затем проверяет извлечённый текст для всех 29 ожидаемых типов. Приватные текст/матрица/отчёт сохраняются в output. Gate требует полного независимого набора, полной матрицы heldout, отсутствия наблюдённых ошибочных возвратов и неверных названий типа, минимум 95% совпадений положительных примеров и 95% корректных несовпадений отрицательных. Это критерий выпуска на данном наборе, а не гарантия точности на любых фотографиях. Политика и модель привязаны к хешам: изменение модели, правил, matcher или reader требует повторной оценки. Отдельно проверяются поворот, размытие, смешанные пакеты, ошибки сервиса и ресурсы при работающих RU/UZ/GLM. Несколько успешных демонстраций не заменяют этот этап.

`prepare_typecheck` отклоняет `provider=xiaomi` без проходящего `shared/var/verification/typecheck/gate.json` для текущих модели и исходников. Shadow разрешён для накопления результатов. Эталонные фотографии, OCR-текст и сами результаты никогда не коммитятся.
